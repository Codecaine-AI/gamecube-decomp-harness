Melee knowledge base redesign

Working doc — draft v2 · 2026-07-02 · companion to 50-knowledge-model.md (current model). Brainstorm only; nothing here is implemented.

1. Organizing principle: maintenance regimes

  • Principle
    • Knowledge is divided by who keeps it true, not by topic.
    • Five regimes.
  • Derived
    • Rebuilt deterministically from the checkout, splits, map, objdiff.
    • Cannot drift; the rebuild is the audit.
  • Corpus
    • Raw external text stored verbatim, searched at need.
    • Nothing interpreted, so nothing to drift.
    • Only staleness vs. upstream, which is tolerable.
  • Ledger (events)
    • Append-only records of what happened (attempts).
    • Facts about the past don't rot.
    • Derived views over the ledger (tactics) are re-extractable.
  • Annotations (beliefs)
    • Machine-proposed annotations of what functions/data mean in game terms.
    • Not authored prose — every annotation carries:
      • evidence refs
      • a content-hash anchor (drift becomes detectable, not silent)
      • a status lifecycle ending in graduation to upstream code
    • See §3.
  • Authored
    • A human writes prose and must keep it true.
    • Deliberately minimized to one thing: standards.
      • Standards have an owner and an enforcement loop (QA fires on every ship, so wrong standards get noticed).
  • Consequence
    • No hand-curated game_concept nodes, no per-area craft briefs.
    • Game understanding enters either:
      • as raw corpus (the wiki, searched at need), or
      • as evidence-backed annotations produced during work
    • Never as unowned summaries.

2. Connection map

  • Reading the map
    • Solid arrows are graph edges materialized at build time; dashed arrows are runtime query paths.
    • The target file is the worker's input and the entry point to everything.
  • Understanding cluster (amber)
    • Bridges the non-semantic code graph and the raw corpus.
    • Annotations cite wiki sections, call edges, PR comments, and attempts as evidence.
    • Graduate into upstream renames/comments — at which point they move into the derived regime and can never drift again.
  • Tactics have no direct edge to targets
    • Reached through attempts (tactic → attempts → targets).
    • A tactic is a view over attempt evidence, not a store.

3. Understanding layer — annotations without silent drift

  • The idea
    • The most valuable and most drift-prone piece: a semantic map of the codebase.
    • What each function does in game terms, linked to the wiki — effectively commenting the code, and eventually naming it.
  • The reconciliation with §1
    • This is not authored prose.
    • It is a second ledger — a ledger of beliefs next to the ledger of events — with five drift controls.
  • Drift control 1 — byproduct production
    • Workers already form these hypotheses during every attempt ("this is the apex-flip state handler; the shockwave spawns in the item file").
    • Today that understanding evaporates when the run ends.
    • Annotations capture it; nobody sits down to author them.
  • Drift control 2 — evidence required
    • An annotation without refs (wiki section, call edge, PR comment, attempt transcript span) cannot be accepted.
    • The annotation is a conclusion; the evidence is inspectable.
  • Drift control 3 — content-hash anchoring
    • Every annotation pins the symbol and a hash of the function it describes.
    • When the function changes or is renamed upstream, the annotation flips to stale automatically.
    • Drift becomes a detectable state, not silent rot.
  • Drift control 4 — consumption feedback
    • Annotations are injected with confidence and status.
    • Workers that rely on one confirm or refute it in their attempt record.
    • A refuted annotation flips status — it doesn't linger.
  • Drift control 5 — graduation
    • The lifecycle ends with the knowledge leaving the ledger: corroborated annotations become upstream naming/comment PRs.
    • Names are the semantic layer in a decomp.
      • Once merged, the annotation's content lives in the checkout — the derived regime, audited by every rebuild forever.
    • The annotations ledger is a staging area, not a permanent store.

Annotation record

{
  "id": "annotation:fn:ftKb_SpecialHi_Enter:role",
  "subject": { "symbol": "ftKb_SpecialHi_Enter",
               "file": "src/melee/ft/chara/ftKirby/ftkirbyspecialhi.c",
               "content_hash": "…" },              // staleness anchor
  "kind": "role",                                   // role | game_link | name_proposal | data_meaning
  "statement": "Enters Final Cutter rise phase; sets vertical velocity from static table",
  "evidence": [
    { "type": "wiki_section", "ref": "Kirby (SSBM)/Up special#Overview" },
    { "type": "call_edge",    "ref": "CALLED_BY ftCo_SpecialHi dispatch" },
    { "type": "pr_comment",   "ref": "https://github.com/doldecomp/melee/pull/…#discussion_…" },
    { "type": "attempt",      "ref": "attempt:run:…#transcript-span" }
  ],
  "confidence": 0.7,
  "produced_by": "worker during attempt:run:…",     // byproduct, not authored
  "status": "proposed",                             // proposed | corroborated | refuted | stale | graduated
  "graduated_to": null                              // upstream PR ref once renamed/commented
}
  • Traversal consequence
    • The classical, non-semantic lookups (opseq, calls, data refs) land you on files.
    • Annotations tell you what they mean.
    • The meaning links onward:
      • wiki sections via evidence
      • related concepts via the functions they annotate
    • File↔wiki deep links accumulate as evidence edges from real work rather than being curated up front.
  • Seeding
    • The existing tree-guide blurbs can be bulk-imported as low-confidence proposed annotations to seed the ledger.

    • Unknown function → CALLED_BY Brinstar map-init → so it's stage-loading machinery.

  • Why this is drift-proof
    • The first four axes need no one to have written anything.
    • The semantic axis strengthens as annotations accumulate from work.

5. Attempt — canonical record

{
  "id": "attempt:pr:2531",                    // or attempt:run:<runId>, attempt:repair:<id>
  "kind": "upstream_pr",                       // upstream_pr | worker_run | qa_repair
  "actor": "human:<login> | worker:<model>",
  "at": "2026-05-14",
  "targets": [
    { "file": "src/melee/ft/chara/ftYoshi/ftyoshispecialhi.c",
      "functions": ["ftYs_SpecialHi_Enter"],
      "before": { "score": 84.1 },
      "after":  { "score": 100.0, "exact": true } }
  ],
  "outcome": "merged",                         // merged | rejected | partial | failed | abandoned
  "failure_class": null,                       // mismatch-pattern category when failed
  "tactics": [
    { "tactic": "tactic:sdata2/anchor-literal", "worked": true,
      "evidence": "diff hunk / review comment / run transcript span" }
  ],
  "annotations_produced": ["annotation:fn:ftYs_SpecialHi_Enter:role"],
  "annotations_relied_on": [ { "annotation": "…", "verdict": "confirmed" } ],
  "evidence_refs": ["https://github.com/doldecomp/melee/pull/2531", "runs/…/summary.json"],
  "extraction": { "by": "postmortem-pipeline@v3", "at": "2026-07-01" }
}
  • Intake normalization is the whole trick
    • past_prs already holds the raw material (postmortems, changed files, review comments, descriptions).
    • Worker runs already produce summaries and failure classifications.
    • One intake pipeline per kind, all emitting this shape.
    • After that, "PRs" stop being a source:
      • they're one kind of attempt
      • the attempt links back to the PR's comments and description for on-demand reading
  • Tactics are a view, not a store
    • A tactic lives on attempts; attempts live on targets; targets are linked (siblings, analogs, peers).
    • So tactic retrieval is graph traversal:
      • by target — "everything ever done to this file, its siblings, its analogs — and the tactics that worked there"
      • by tactic — "this symptom → which tactics, validated on which attempts"
    • Vocabulary seeded from the ten mismatch-pattern categories currently hardcoded in mismatch-patterns.ts.
    • The extraction pass is re-runnable over the ledger, so a better extractor improves every tactic retroactively.

8. Open questions

  • Annotation writer contract
    • Workers must emit annotations (and verdicts on annotations they relied on) as part of the attempt record — a prompt-contract change.
    • What's the minimum viable shape that doesn't burden the matching loop?
  • Corroboration threshold
    • How many independent confirmations (or one strong evidence type, e.g. an upstream rename) before proposed → corroborated?
    • Who/what adjudicates — the curator job?
  • Graduation pipeline
    • Who drafts upstream naming/comment PRs from corroborated annotations — a dedicated agent lane, or bundled into match PRs?
  • CALLS edge source
    • Clang AST pass vs. ctags-level heuristics vs. map/objdiff data.
    • Is "VS Code-grade" required, or are ~90%-accurate heuristic edges enough for injection ranking?
  • Symptom vocabulary
    • Start with the ten mismatch categories as controlled vocabulary; let signatures (section, instruction class, diff shape) grow under them.
    • How structured does the trigger need to be before it beats text search over objdiff output?
  • Negative results
    • "Tactic tried, didn't work" requires workers to self-report tactics — same prompt-contract change as annotations.
    • Worth it from day one?
  • Sibling extraction
    • Naming-convention rules (character prefixes, move suffixes) are mechanical but Melee-specific.
    • Where do they live — project config or builder code?
  • Crosswalk scope
    • Today it covers ft chars.
    • Extend the same mechanical treatment to stages/items (gr*/it* → stage/item pages)?
