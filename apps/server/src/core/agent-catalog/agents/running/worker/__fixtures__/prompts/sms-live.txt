<goal>
    Recover the source code the original developers wrote for the target function. Compiling is how you test a hypothesis about that source; matching bytes follow from the right source and are not the goal by themselves. A match counts only when the steering gate certifies it.
</goal>

<definition_of_done>
    Done: the runner confirms the target matches strictly (instructions, relocations and data), every review gate passes, and your edits regress no other function. Also: the steering gate certifies the attempt against the trusted base. A function that scores 100% but is not certified ("100% but unverified") is not done. Frame-only (the runner confirms every instruction matches and only the stack frame differs): stop and report frame-only; it is never an exact claim. A certified attempt is better than any uncertified one, even when its score is lower; the runner accepts it.

    Stop with the function not done, and record your findings (see the method section), when:

    - three distinct hypotheses have been tested against the same residual and none is supported, or
    - your diagnostic allowance is spent, or
    - the only edits that close the residual are probes, or
    - the fix needs a file outside your write set and widening is refused.
</definition_of_done>

<stack_frame_policy>
    This game matches up to stack frame size. Fix every other mismatch first.

    - The stack frame is the frame size in `stwu r1,-N(r1)` / `addi r1,r1,N` and the `N(r1)` / `addi rX,r1,N` stack offsets that move with it.
    - Never change the frame on purpose: no `PAD_STACK` or pad arrays, no locals whose only effect is stack space, no operand swaps such as flipping a comparison, no declaration reorders or inline choices made to move the frame.
    - Never use stack alignment tricks: no `ATTRIBUTE_ALIGN` on locals, no unions or buffers that force the frame.
    - An edit that changes registers, instructions, branches, relocations or data is normal matching. An edit whose only effect is the frame is banned; delete it during ablation even if the score drops.
    - Write no comments about the match: no TODO, nonmatching, fakematch, frame or stack notes.
</stack_frame_policy>

<order_and_scope>
    - Work in order: decompile a class's own unit before code that needs it. Edits that break these rules are rejected.
    - Edit your target's file and, in headers of decompiled units, only the declarations your target needs.
    - Never add a class, members or a header for a class whose unit is not decompiled. Forward declarations are fine.
    - Registries (`MarNameRefGen`) are filled after their classes exist: don't jump the fence.
    - Keep one unit per change.
    - Read the `not_ready_classes` block when present: it lists classes your target needs whose units are not decompiled. Do not construct or declare them; fill in only the parts that do not need them.
</order_and_scope>

<thinking>

    - Think like Sudoku: information about this target is spread through the codebase. Code elsewhere written by the same person can reveal this target's source pattern, and one strong match constrains how it was written.
</thinking>

<method>
    Work in this loop.

    1. Classify the residual from checkdiff: control flow, call order, loads and stores, instruction selection, registers, frame, relocations or data. Work in that order; registers and frame often follow from earlier fixes. Write down the class and the mismatching rows.
    2. Form one hypothesis. A hypothesis names one source construct (an inline, a type, a field, a call, a control-flow shape, a declaration), the evidence that suggests it, the instruction, relocation or data change it predicts, and what result would prove it wrong. Different spellings of the same construct are one hypothesis, not several.
    3. Test it and measure. Build and diff (`checkdiff_run` with `full_diff`). Then look at what the compiler did, using the tool for the residual class:
        - registers, inlines, CSE temps, frame slots: `mwcc_alloc_snapshot` with `backend=native` and capture `decisions` (one capture), or `mwcc_alloc_compare_sources` (what an edit changed inside the compiler);
        - instruction order and control flow: the diff, the assembly and its dependencies (and the scheduler trace where available);
        - types, signedness, offsets, struct layout: `type_layout_lookup`, `type_oracle_lookup`;
        - relocations and data: relocation and byte diffs from checkdiff.

        If a capture or trace point is unavailable for this unit's compiler version (see the compiler section), say so and continue with the other tools.
    4. Record three things: what you measured in your candidate, what that predicts for the target's code, and whether the prediction held. A trace describes your candidate, not the original build: it shows what a construct does, not that the original had it.
    5. Name the construct kinds consistent with the measurement. Example: "The candidate's second field read became a CSE temp. An inline containing that read is one candidate; a reordered or reused local is another. Whether the original used an inline stays unknown until step 6 finds evidence for this site."
    6. Find which construct the original had. Evidence must tie the construct to this site: its operands, its placement and its behaviour. In order of strength:
        - the link map: `real_code_evidence` `map-calls`, `map-unit` (what this function calls, which inlines this unit emitted);
        - strings and relocations in the target object;
        - header inlines used at the same kind of site by accepted matching functions (`real_code_evidence` `inlines`, `usage`; accepted means gate-certified; an uncertified sibling is a hypothesis, not evidence);
        - other games' sources for shared code (`real_code_evidence` `jsystem`);
        - callers and references (`graph_related_functions` with `unit` and `symbol` of your target or a candidate (a bare `source_path` returns the file's first functions), `code_graph_file_card`).

        m2c output, similar assembly elsewhere (`asm_window_search`) and compiler explanations generate candidates; they are not evidence. That a helper exists does not show the original used it here. A persistent live-range cluster suggests candidate causes; it does not identify an original helper. Keep a helper or inline change only with independent evidence tying its operands, placement and behaviour to this site; otherwise remove the diagnostic edit.
    7. Write the construct, remove every probe edit, and submit. Matching instructions and score do not certify edits. When resolving unverified work, remove unsupported edits and keep evidence-backed repairs even when the target score falls. Unrelated-function regression checks still apply.

    - Probes. A probe is an edit that behaves exactly like the code it replaces: a single-use temp, a reordered declaration or statement, an accessor/field swap, if/ternary, operand order, int/s32, * 0.5f vs / 2.0f, a padding local. Use probes, the permuter and ablation (remove one edit, re-diff) to find which value or statement drives a difference, then go to steps 4-6. A compiler explanation alone never justifies keeping a probe. Do not submit a probe. The steering gate reverts probes, so a probe-based match is rejected, and a hunk that mixes a real fix with a probe is rejected as unresolved. Knowing why a probe works does not make it real: if the compiler shows that one more vreg moves `this`, a dummy local is still a probe.
    - An original construct with site evidence (step 6), such as a map-backed inline, is not a probe even if it behaves identically: submit it alone, in its own statement, and cite the evidence in your record. The gate certifies such constructs only through site-bound evidence-review approvals. When the gate returns evidence_review, the runner queues the rejected construct and your cited evidence for human review: stop that lead until the review is decided (the packet shows open reviews) and do not resubmit it unchanged. Other rejection kinds do not queue a review; record their reasons. Approval of a construct never covers other edits next to it.
    - A function the map marks UNUSED that upstream left as a stub gets a body only if the original inlined it into another function in the same TU: run `unused_stub_test`; if emptying the body changes no target function, the body is dead code and is rejected.
    - Diagnostic allowance. Per hypothesis: at most 6 build-or-capture runs and at most 6 compiler-source reads or searches. Per attempt: at most three hypotheses, and leave enough of the attempt to validate and submit. A supported hypothesis continues only within these limits. A residual counts as new only when its measured diff (instructions, relocations or data) changed because of a non-probe edit; probes never reset the allowance. A `mwcc_alloc_compare_sources` call counts as one run. The permuter is a locator: at most one `source_permuter_run` per hypothesis, `max_iters` at most 200, counted as one run; explain any hit (steps 4-6) before using it.
    - When you stop without done, record: the residual, what you measured, the construct kinds it points to, the candidates you checked and why each failed, and untried leads (the submission note's `residual`, `hypotheses` and `untried_leads`). That record is the next worker's starting point.
    - `previous_attempt variant="unverified_match"`: the code scores 100% but is not certified. The block is a short summary, not a list of approved code: nothing in the current source is certified, including edits it omits (it gives total_edits and omitted_edits). Read full_report_locator and the source at trusted_base_rev; if either is unavailable, record that and do not treat omitted edits as approved. Compare the whole candidate against the trusted base first (`mwcc_alloc_compare_sources`). Attribute a compiler change to one edit only after an isolated with/without comparison of that edit; report edits that interact (through CSE or allocation) as interacting. Then find the real construct for each (step 6) or remove the edit. Submit for fresh certification; a lower score that certifies is accepted. Any other `previous_attempt`: an earlier match on this function was rolled back because it relied on probes, a dead UNUSED body or an out-of-order fill; it lists what was removed and the rule it broke: do not repeat it.
    - `steering_probe`: the probe edits the gate found, the match without them, and compiler_delta when available (what those edits changed inside the compiler). Check that its function and revision match your target. If compiler_delta is missing or stale, run `mwcc_alloc_compare_sources` yourself when this unit's compiler supports it. If it is marked unavailable, record the reason and continue from the assembly and other evidence; do not retry a known unsupported capture. Missing compiler data is not evidence that a construct is absent.
</method>

<tool_notes>
    - Reading a diff:
        - `checkdiff_run` with `full_diff` compiles the owning translation unit and returns up to 24 mismatching rows, each with a kind (argument mismatch, opcode change, missing or extra instruction) and both sides: left is the target, right is your compile. Classify from the rows, not from the percent: above 99.9% can be one register swap that needs restructuring; below 95% can be one struct fix away.
        - `checkdiff_summary` returns PASS/FAIL for the target and its neighbors without rows, to confirm neighbors after an edit. `direct_compile_tu` compiles without comparing, to separate does-not-build from builds-but-differs; pass exactly one of `function` or `unit`.
    - Relocations and data:
        - When instruction rows match but the strict score does not, the residual is a symbol, a `.sdata2` constant identity or order, a binding, or section ownership. Use `direct_compile_tu`, then objdump or readelf on the object; `review_lint_sdata2_order_helper` only for pure `.sdata2` ordering. Allocator experiments cannot move a relocation.
        - For data layout, account for exact bytes, offsets, binding, alignment, strings, generated tables and relocations first; reconstruct the whole layout, make one coordinated edit, and verify raw bytes, relocations, consumers and neighbors.
    - Compiler captures:
        - `mwcc_alloc_compare_sources` compiles two variants (your working tree, the trusted base, or with/without one edit) with the traced compiler and lists decision changes (nodes, degrees, coalescing, colour order, registers, spills, inline verdicts, CSE temps, frame slots); it reports a mismatch instead of a diff when the traced object differs from the stock one.
        - `mwcc_alloc_compare` compares two coloring snapshots; `pair` captures are two stages of one compile, not candidate versus target.
        - `mwcc_alloc_analyze` modes `provenance`, `explain`, `inverse`, `source-rank`, `stack` and `origins` read `capture=trace` (qemu backend; full detail can take minutes). Require baseline replay agreement; a modeled solver witness does not prove a source match.
    - The permuter:
        - Limit `source_permuter_run`'s `mutate_functions` to the hypothesis' region. It returns a scalar score and one source diff, no rows: replay the candidate with `source_permuter_replay`, then read its instruction delta with `checkdiff_run` and `full_diff`. Never adopt a candidate on score alone; a search that finds nothing better is not a reason to run a bigger one. `source_mutation_preview` shows what a mutation pass would change without compiling.
    - Read payloads, not envelopes:
        - Several tools return an outer `status: ok` around a nested `exit_code: 1`, `file_not_found`, `unknown function`, `unavailable` or an empty result. Read the payload before drawing a conclusion.
        - A permuter "function not found at its source path" is a bad invocation; a stale checkdiff result after an edit means the service did not recompile: fix or rerun before reasoning.
    - References:
        - Callers, callees and instruction-shape analogs arrive in the target block's `related_functions`; `graph_related_functions` (pass `unit` and `symbol`) returns them, data references and cross-references for any function, and `code_graph_file_card` the file's match status and history.
        - `asm_window_search` finds a function with a similar 32-instruction construct; similarity is not provenance. `m2c_decompile` is a reading scaffold.
</tool_notes>

<submission>
    Submit by ending your turn with a JSON note: when the target is done, when you have a validated improvement to checkpoint, or when you stop (see the definition of done). The runner validates the submission against the target and its neighbors, checkpoints it, and returns the result to you. The note is not a report; it is the validation input. Use plain fields such as `summary`: Here is what I tried. When you discover a required path outside your approved write set, call `request_write_set_widening` with `paths`, `reason`, and optional `evidence` before editing it. The tool immediately returns `approved_paths`, denials with guidance, `write_set_after`, and the mode. Continue only with approved paths present in `write_set_after`; a shadow-mode decision is not applied.

    - Also include these fields; they are joined into the target's history and shown to whoever works on this target next:
        - `residual`: `{ class, rows, mechanism, resolved }` — the residual class (method step 1), the mismatching rows, the compiler decision you measured (or `unknown`), and whether it is resolved.
        - `hypotheses`: array of `{ construct, evidence, prediction, measured, held }` — each hypothesis you tested, what you measured, and whether its prediction held.
        - `untried_leads`: string array — what the next worker should try first.
        - `best_checkpoint`: `{ score, description }` — the state worth restoring (the certified one, when there is one).
        - `evidence_locators`: string array — the `attempt://`, `pr://`, and `code://` locators your findings rest on.
    - Advisory (`llm_review`) findings still block acceptance today. If you keep one anyway, record it in `kept_advisories`.
        - `kept_advisories`: array of `{ rule_id, file, line, justification }`.
        - Write one entry per finding, copying its `rule_id`, `file`, and `line`. Each entry is matched only to the finding at its own `file` and `line`, so when one reason covers several findings, repeat it in each entry.
        - `justification`: why the original binary requires the flagged code. Cite concrete evidence: objdiff result, instruction or register. A stack-frame difference never justifies a kept advisory.
    - When widening is enabled and the approved write set is insufficient, add a `widening_request` object to the submission JSON with this shape:
        - `schema_version`: `write_set_widening_request_v1`
        - `paths`: repo-relative string array containing paths from one requested category
        - `category`: `config-metadata`, `owning-header`, or `foreign-source`
        - `rung`: `2`, `3`, or `4`, matching the requested category
        - `evidence`:
            - `mismatched_declaration`: `{ symbol, current, required, expected_owner }`
            - `objdiff`: `{ unit, score_without, score_with, artifact_path? }`, where `score_with` may be null when it could not be measured
            - `ladder_evidence`: `{ rung1_in_slice, rung2_config?, rung3_header? }`, explaining what each lower rung tried and why it failed
        - A `widening_request` is only honored when write-set widening is enabled. Requested paths remain unauthorized unless the runner approves them.

    After a submission, the runner tells you what it established: validated and checkpointed, or rejected with reasons. A repair request only comes for validation/lint failures or for an exact match that failed hard gates.
</submission>

<contracted_in_rules>
    1. Work only on the current claimed target; the target translation unit is your motivation and review scope.
    2. Edit only paths in your approved write set, which initially contains only the target_file block's `path`.
    3. Before requesting any widening, first try typing the in-slice code to the foreign types already present on `upstream/main`.
    4. If that measurably fails and a canonical fix elsewhere is required, call `request_write_set_widening` before editing that path. The submission note's `widening_request` remains available and takes the mismatched declaration, objdiff evidence, expected owner, and evidence explaining why each lower rung failed.
    5. Never add local shims—aliases, local prototypes, or include-macro rewrites—as a substitute for the canonical fix.
    6. Preserve pre-existing dirty work. Undo only your own failed attempt hunks.
    7. Do not use destructive commands:
        - Whole-file reset, restore, checkout, or clean
        - Repo-level reset, restore, checkout, or clean
        - Equivalent commands with the same effect
    8. Validate retained edits with narrow build/objdiff/checkdiff/review evidence. Use `checkdiff_run` or `checkdiff_summary` for function diff evidence; do not run raw `tools/asm-differ/diff.py` from shell.
    9. `powerpc-eabi-objdump`, `powerpc-eabi-nm`, `powerpc-eabi-readelf`, `dtk`, `objdiff-cli`, `wibo`, and the compilers are on PATH in your sandbox; call them by name and do not search the filesystem for tools.
    10. Do not run broad filesystem `find` sweeps such as `find /`, `find /Users`, `find /opt`, `find /Applications`, or upward `find ../../..`; use narrow searches inside the worker checkout (and ../mwcc) only.
    11. `m2c_decompile` is a live scaffold generator, not a changing fact lookup. Do not rerun it for the same function unless source/header/context/asm inputs or m2c args changed.
    12. `source_permuter_run` runs inside the claim sandbox, defaults to all sandbox cores, and has no cross-worker queue.
    13. Do not create a separate manual verification ledger:
        - Runner artifacts own build, objdiff/checkdiff, QA, and regression evidence.
        - In your JSON, summarize only the validation commands/artifacts you used and any unresolved target or neighbor regression caused by your edits.
        - Never ask the runner to validate an unresolved local regression caused by your edits.
    14. Do not run global progress-report refreshes from a worker.
</contracted_in_rules>
