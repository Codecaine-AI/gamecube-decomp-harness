## Scope and canonical identity
This TU consists of the complete 57-line `ftdonkeyheavywalk.c` and 12-line `ftdonkeyheavywalk.h`. It defines six externally visible functions: two entry helpers and four HeavyWalk callbacks. The header declares only the four callbacks; the entry-helper declarations are located in `ftdonkeyheavywait0.h`, as confirmed by pinned-source symbol searches. The canonical entry names remain `ftDk_MS_341_800DFA98` and `ftDk_MS_341_800DFAE4`. `ftDk_HeavyWalk_CheckInput` and `ftDk_HeavyWalk_Enter` are well-supported naming hypotheses, not canonical identifiers. The analogous canonical `ftCo_Walk_CheckInput` and `ftCo_Walk_Enter` supply naming-convention evidence independently of the rendered substitutions. ## Entry and configuration
`ftDk_MS_341_800DFA98(HSD_GObj*)` calls `ftWalkCommon_800DFC70`. On success it invokes `ftDk_MS_341_800DFAE4(gobj, 0)` and returns true; otherwise it returns false without initialization. The shared predicate is read-only and accepts `lstick.x * facing_dir >= walk_stick_threshold`, including equality. HeavyWait0 invokes this predicate only after its throw, jump-input, and turn predicates fail. This is not a universal guard on the initializer: `ftDk_MS_341_800DFAE4` is unconditional and is also used for active speed-tier changes. Sources: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftDonkey/ftdonkeyheavywalk.c#L14-L32; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftwalkcommon.c#L58-L97; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftDonkey/ftdonkeyheavywait0.c#L40-L49.

The initializer resolves Fighter and obtains `fp->x2CC` through `getFtSpecialAttrs2CC`, treating it as `ftDonkeyAttributes*`. It forwards `motion_state + 1`, flags zero, the unchanged `argf`, fields `x8`, `xC`, `x10`, `x14`, `x18`, `x1C`, and unity to `ftWalkCommon_800DFCA4`. The six fields respectively supply slow/middle/fast animation-frame parameters and slow/middle/fast animation-rate denominators. Their source declarations are floats; their compiled offsets are not proved here. The shared initializer stores unity as `mv.co.walk.accel_mul`, classifies absolute ground speed, changes motion to base plus the selected walk type, calls `ftAnim_8006EBA4`, and stores the current ground velocity, base, and six animation parameters. Fast comparison is tested first, then middle, both with inclusive `>=`; remaining values select slow. ## Active callbacks and consumers
The active Donkey motion table installs all four callbacks for HeavyWalkSlow, HeavyWalkMiddle, and HeavyWalkFast. This is active table evidence, not an interpretation of the `MS_341` numeric name. The same table separately installs CargoWalk callbacks for ThrowFWalk states; consequently the speculative `maybe Cargo Hold` attribute comment is not sufficient to identify this TU as opponent-carry CargoWalk. The runtime attribute value that makes `motion_state + 1` address those entries is not established by a compiled data artifact in this pass. Source: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftDonkey/ftdonkey.c#L40-L194.

`ftDk_HeavyWalk_Anim` forwards its object unchanged to `ftWalkCommon_800DFDDC`. That routine uses saved walk target `x0` when ground-friction multiplier is less than one, otherwise actual ground velocity. Nonpositive facing-relative movement sets animation rate to zero; otherwise absolute movement is divided by the selected tier's rate parameter. There is no default arm assigning a rate for an invalid motion offset. Sources: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftDonkey/ftdonkeyheavywalk.c#L34-L37; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftwalkcommon.c#L99-L128.

`ftDk_HeavyWalk_IASA` evaluates `ftCo_80094EA4`, `ftDk_MS_347_800E0378`, and `ftDk_MS_341_800DF938` in that strict order. Any true result suppresses all remaining calls. Only three false results reach `ftWalkCommon_800DFEC8(gobj, ftDk_MS_341_800DFAE4)`. The first predicate checks an existing held item and derives a HeavyThrow transition from A/B plus main-stick input or from C-stick input, returning true only when it changes the motion. The second obtains jump input and calls `ftDk_MS_348_800E04A4`; its immediate destination must not be inferred from the numeric helper name alone. The third conditionally initializes the attribute's base waiting motion. The shared IASA fallback calls the entry callback synchronously only if the newly classified motion differs from the current motion. It maps current animation phase to the destination tier's frame parameter, using two intermediate s32 conversions, and passes that integral result back as float. It neither saves the callback nor allocates callback context. No callback runs if the tier is unchanged. Source: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftwalkcommon.c#L130-L170.

`ftDk_HeavyWalk_Phys` forwards to `ftWalkCommon_800E0060`. The shared physics computes stick-scaled acceleration plus signed base acceleration, and target velocity `stick.x * walk_max_vel * accel_mul`. Base acceleration uses the positive sign only for stick.x > 0, including the negative branch at zero. For a nonzero target, taper applies only when `0 < gr_vel / target_vel < 1`; neither endpoint is tapered. It saves `target_vel * p_ftCommonData->x440`, calls the friction-aware velocity helper, then applies ground movement. HeavyWalk supplies unity rather than reproducing ordinary Walk's optional metal, scale, and attached-object multiplier branches. ## Preconditions, ownership, exceptional values, and limits
The six functions borrow an HSD_GObj pointer. They neither allocate nor free objects and perform no local ownership transfer. They assume valid Fighter data, valid special attributes, and initialized common walking state. The TU does not independently validate held-item presence, ground state, motion base, float ranges, or null object/attribute pointers. It does not establish general object lifetime outside these calls. The seven parameter subjects have no baseline facts; source signatures establish pointer and float roles, not physical register allocation. In particular the `#r4` locator does not prove the float parameter is passed in integer register r4.

At ordinary IEEE comparison semantics, NaN input fails the entry comparison; NaN speed causes both tier comparisons to fail and selects slow. Infinite speeds and thresholds are not sanitized. Animation denominators can be zero or nonfinite, and the phase-rescaling path divides by an animation-length result without a local zero/finite check. Float-to-s32 conversion outside the representable domain has no portable safe result established here. An invalid active tier can leave animation rate uninitialized. These are unguarded preconditions, not claims that malformed data occur in normal gameplay. Exact target floating-point and conversion behavior needs compiled evidence. Signed `motion_state + 1` also presumes a valid non-overflowing state base.

The source proves literal zero and unity argument flow, but not an eight-byte `.sdata2` pool, constant order, storage encoding, or section association. No compiled artifact was assigned. Heavy-item walking is supported by the active HeavyWalk table and item-throw integration; uniqueness across the roster and an unconditional equivalence to ordinary walking speed are not proved. All retained statements are source-level semantic findings, not assertions of binary matching or object layout.
