## Input and event lifetime
The IASA bodies are semantically equivalent. When `cmd_vars[0] == 0` and absolute horizontal stick input exceeds `x34`, they compute `x38 * ((abs_x - x34) / (1.0 - x34))`, convert degrees to radians and negate the candidate for positive horizontal input. They replace `lstick_angle` only for strictly greater absolute magnitude; equal magnitude cannot reverse its sign. There is no local clamp or attribute-range validation.

Independently of that phase guard, `ftCheckThrowB3` consumes the throw event before testing the `x30` stick threshold. Insufficient input therefore still consumes a set event. Passing input assigns facing from stick sign and rotates part 0 by `HALF_PI * facing_dir`; this is not an unconditional facing reversal. Neither callback directly requests a state transition. ## Physics and phase lifetime
Ground-family physics tests `ground_or_air == GA_Air`; every other value calls `ft_80084FA8`. In air with `cmd_vars[2] == 0`, it calls `ft_80085154`, derives horizontal sign using negative versus nonnegative velocity, and negates horizontal velocity if that sign differs from facing. Negative `x6A4_transNOffset.y` sets `cmd_vars[2] = 1`. The alternate airborne branch calls `ftCommon_Fall(fp, x44, x48)` and `ftCommon_8007D344` with zero and both common drift parameters multiplied by `x28`.

Aerial-family physics first tests `cmd_vars[0]`. Zero selects common gravity and terminal velocity followed by `ftCommon_8007CF58`, irrespective of `cmd_vars[2]`. Nonzero with zero `cmd_vars[2]` selects `ft_80085154`, scales all three self-velocity components by `x40`, performs the same horizontal orientation correction and sets the same translation-offset latch. Both selectors nonzero select the attribute-driven fall/drift branch. This callback has no ground/air test.

The latch affects later invocations, not an earlier branch within the same invocation. It is not permanent: both entries reset it. This file never advances `cmd_vars[0]` from zero, so activation timing depends on external writers. Negative translation offset does not establish a physical velocity apex; multiplication by `x28` proves scaling, not necessarily reduction. These distinctions support proposal 0 and the accepted numerical deferrals. [Physics evidence](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMars/ftmarsspecialhi.c#L141-L217)

## Collision and landing handoff
Both collision callbacks have identical ordered branches. Non-air values call `ft_80084104`. In air, zero `cmd_vars[0]` or nonnegative vertical velocity selects `ft_80083B68`. Otherwise, zero `cmd_vars[1]` is set to one and that invocation still calls `ft_80083B68`. Only a later eligible invocation supplies `ftCo_80096CC8` and `ftMs_SpecialHi_80138884` to `ft_800831CC`. The delay is an eligible invocation, not necessarily a globally measured frame; subsequent nonnegative velocity still selects the earlier branch. Callback supply does not prove callback invocation or accepted contact.

The wrapper reads Fighter userdata and `MarsAttributes.x2C`, then unconditionally requests `ftCo_LandingFallSpecial_Enter(gobj, false, x2C)`. The common entry checks `ftCo_800C5240`: success enters HammerLanding; otherwise it enters LandingFallSpecial with interrupts disallowed and animation rate `(0.1F + fp->x2EC) / landing_lag`. Proposal 1 correctly preserves this exception rather than claiming unconditional duration consumption. The baseline's 34-frame gameplay description is not a verified constant here. `ftMs_SpecialHi_CheckLanding` remains a naming convention supported by inherited canonical Luigi analogy, not a claim that the wrapper is a contact predicate.
