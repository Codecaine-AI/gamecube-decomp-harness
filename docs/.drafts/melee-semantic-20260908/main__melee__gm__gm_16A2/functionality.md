## Shared opponent preparation and runtime spawning

`gm_16A2.c` owns two static runtime objects. The primary object supplies generated-opponent configuration, parallel costume/character/copied-fighter tables, slot-to-sequence mappings, counters, flags, combat parameters, and two distinct callback slots. The secondary object stores character/costume pairs for an auxiliary roster display. Source declarations establish their static lifetime, but this review makes no compiled section-placement or ordering claim.

`gm_8016A22C` clears exactly a 0x1C0-byte prefix, stores nineteen configuration arguments, caps only values of `x9` above five, defaults model scale to 1.0, and uses the byte-stored `x7` as the generated roster length. Only the costume/shape table receives a `-2` terminator; the parallel character and copied-fighter tables derive their extent from it. Character generation supports fixed, random two-candidate, and sparse unlock-gated alternate modes. Randomized costume allocation filters by character, whereas uniform allocation overwrites the entire active prefix on each invocation. Unsupported modes have no corresponding write branch. Costume-count queries precede the character-0x21 no-write guards.

The copied-fighter generator excludes character index 4 and locked characters, shuffles 27 positions, and prunes only the first 26 positions after the sixteenth eligible entry. Its index wraps modulo 27 only while skipping `-1`; successful selections increment without an unconditional wrap. Resource-preparation helpers enumerate copied-fighter/Kirby-costume combinations and call the Kirby loader rather than granting an ability. Archive and joint loads are cache-guarded, while the downstream effect-loading call remains observable on repeated requests.

The slot initializer enables spawning, clears completion, reserves available slots up to the configured limit, and assigns team 4 to every flagged slot, including previously flagged slots. The spawner considers flagged slots in numeric player state 0, decrements the unspawned count before indexing the tables, configures CPU/player attributes, invokes the optional per-slot hook, and then creates fighters and initializes interfaces. The controller-index helper returns a collision indicator 0 or 1, not the matching player's slot. The remaining-opponent display query instead counts non-NA flagged slots in state 2. Completion uses a third predicate: no non-NA flagged slot with nonzero stocks remains after the queue reaches zero.

The per-slot initialization callback is distinct from the route callback. Route dispatch clears its slot only after an exact return value of 1. Completion disables spawning before invoking the route callback; a callback returning another value remains installed but is not automatically retried by the now-disabled spawner. A teardown caller passes numeric 2 through the Boolean-shaped dispatch interface, so the argument domain should not be normalized without further evidence.

## Cross-file lifetimes and presentation

The primary state is shared by Event Match, traversal encounters, and regular single-player setup, including the final All-Star 25-opponent configuration. `StartMeleeRules.x54` publishes a live alias, not a copy. Adventure code acquires costume and copied-fighter pointers before reconstructing shared state and reads them afterward, demonstrating that these are live aliases across initialization.

The secondary roster uses two declared 28-byte signed arrays. Append searches positions 0–26 and returns an insertion index; prepend returns the resulting length. Both preserve a trailing `-2` on ordinary inputs and fail without writes when no searchable terminator exists. Retirement checks only whether rules `x58` is non-null, then searches the singleton itself backward, including the terminator position, and changes a matching costume entry to `-1`. Sentinel-valued inputs are not locally rejected. Runtime zero-stock teardown uses this operation to retire roster entries; it is not itself costume selection.

All-Star setup populates this roster with upcoming opponents. The stock interface maintains a separate icon-object lifetime and uses `-1` to hide entries and `-2` to terminate ordinary display processing. Its 130-iteration copy/update bounds do not establish 130-byte source arrays: the declared arrays remain 28 bytes, leaving a cross-file capacity mismatch unresolved. The update loop also contains a terminal cleanup loop that repeatedly indexes `x10C[i]`, rather than its loop variable; this review does not silently repair that behavior.

`unk_10_b3`, set by `gm_8016A434` and read by `gm_80169394`, selects auxiliary stock-display initialization. It must not be confused with `unk_10_b4`, which applies player flag bit 5 and CPU type 0x1B. The wireframe predicate likewise has broader behavior than literal character identification: flagged players with an initial opponent count above one also select its alternate KO-effect branch.
