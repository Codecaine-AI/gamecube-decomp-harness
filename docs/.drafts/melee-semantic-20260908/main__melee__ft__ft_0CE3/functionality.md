# Fighter-side Fire Flower shooting

## Scope and identity
The owned translation unit is `src/melee/ft/ft_0CE3.c`, comprising 274 lines and fourteen function definitions. It implements entry, ground/air conversion, accessory processing, damage synchronization, and paired Anim/IASA/Phys/Coll callbacks for Fire Flower shooting. The active motion table installs both callback suites, and the item-kind dispatch calls the two entry routines specifically for `It_Kind_F_Flower`; this identification is not inferred merely from a numeric state name. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftmotionstates.c#L1806-L1827 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CDD.c#L13-L53.

Canonical symbols remain authoritative. The rendered aliases `ftCo_FireFlowerShoot_Enter`, `ftCo_FireFlowerShootAir_Enter`, `ftCo_FireFlowerShootAir_Land`, `ftCo_FireFlowerShoot_GroundToAir`, `ftCo_FireFlowerShoot_Take_Dmg_Cb`, and `ftCo_FireFlowerShoot_Accessory4` are plausible role names, not recovered original names. Canonical `mv.co.itemthrow.facing_dir` behaves here as a countdown, distinct from the actual `Fighter.facing_dir` used for emissions and effects. The canonical code decrements `mv.co.itemthrow.x4` but tests and resets `mv.ca.specialhi.vel.x`; equivalence of these expressions requires object-layout evidence and remains unresolved. No Captain gameplay behavior follows from that alternate union-member spelling.

## Entry and conversion
`ftCo_800CE3E0` clears `throw_flags`, initializes itemthrow.facing_dir and x4 from common-data x5A8 and x5AC, clears x8/xC/x10/x14, enters FireFlowerShoot with flags 0, frame 0, rate 1, and trailing arguments 0/NULL, calls `ftAnim_8006EBA4`, then installs accessory4 and take-damage callbacks. `ftCo_800CE480` performs the corresponding FireFlowerShootAir entry and additionally calls `ftCommon_ClampAirDrift`. Neither entry checks the object, Fighter, common-data pointer, or held-item kind locally. The observed caller supplies the item-kind selection. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L15-L48.

`ft_800CE528` calls `ftCommon_8007D7FC` and enters FireFlowerShoot; `ft_800CE5A0` calls `ftCommon_8007D5D4` and enters FireFlowerShootAir, then clamps drift. Both pass the current animation frame and frame-speed multiplier with mask 0x0C4C5880 and explicitly reinstall both callbacks. They do not repeat the fresh-entry variable resets. Passing frame and speed is proved; exhaustive preservation semantics of the mask and all move-variable lifetime effects are not established here. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L50-L75.

## Accessory processing
`ftCo_800CE650` returns without its processing when item_gobj is NULL. Otherwise, absence of held A permanently latches xC to 1 until fresh initialization. If x10 is below common-data x5B0 it increments by 1; only afterward, if still below x5B0 and pressed A is present, it resets to zero. This is not a saturating clamp: fractional thresholds can be overshot, and a press on the update that reaches the threshold does not reset it. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L110-L122.

A true `ftCheckThrowB0` result sets x14=1. The initial feedback branch tests `it_8026B594`: zero selects effect 0x3FF at the root-joint position and sound 0xEE; nonzero selects effect 0x405 at the transformed item offset and sound 0xEF. An emission-attempt block obtains and transforms the item offset, calls `it_80292F14` when the predicate is zero, or calls `ftCommon_8007ECD4(fp,1)` otherwise. It increments x8 in either branch, including unsuccessful/empty attempts. After increment, `frame % interval == interval - 1`, with interval common-data x5B4, invokes `ft_800892A0` and `ft_80089824`. A further predicate read after the attempt gates effects 0x3FD and 0x3F3 and `ftCommon_8007EBAC(fp,1,0)`. Therefore that feedback can differ from the pre-shot feedback when the item resource changes. Animation rate is then set to zero. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L123-L172.

The active block is a separate subsequent `if (x14 == 1)`, not an else branch: it runs in the same invocation that activates firing. It decrements x4, tests/reset the alternate `mv.ca.specialhi.vel.x` expression, and potentially repeats the audiovisual feedback. It separately decrements itemthrow.facing_dir; at <=0 it reloads x5A8 and repeats the emission-attempt/count/modulo block. Thus sufficiently short countdowns can produce an initial and recurring attempt in one invocation. Completion is checked after these operations and requires x8>=x5A4, xC!=0, and x10>=x5B0. It clears x14, restores rate 1, and requests rumble removal through `ftCommon_8007ECD4(fp,1)`, not a direct item-state cleanup. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L173-L229 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftcommon.c#L1181-L1186.

The Fire Flower offset helper writes (0,5.5,2.5). `ftCo_800CDE94` copies the offset, divides it by fighter scale.y when that scale differs from 1, then transforms it through the configured item-holding joint matrix. `it_80292F14` only emits when xD4C>0: it optionally spawns effect 0x473, decrements xD4C, forwards the item owner, transformed position, ignore-item ID and direction to `it_802996D0`, and refreshes its ignore-item ID every six successful calls. The fighter's x8 is therefore an attempt count, not proof of successful resource-consuming emissions. The exact semantic contract of `it_8026B594` was not independently established in this review, so its rendered `itIsOutOfAmmo` name is not treated as proof. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itfflower.c#L123-L149 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CDD.c#L79-L97.

## Damage and animation synchronization
`ftCo_800CE620` only forwards a non-null held item to `it_80292EAC`. That helper changes item states 3 or 4 to 5 with ITEM_ANIM_UPDATE, doing nothing for all other switch values. Active item-table entries 2–5 share `itFflower_UnkMotion5_Anim`; pickup selects state 2, states 3/4 progress to 4 at animation completion, and state 5 returns to 2. This supports describing state 5 as a closing held-use phase, without inferring behavior from the UnkMotion name alone. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L78-L84, code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itfflower.c#L29-L42, code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itfflower.c#L94-L121 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itfflower.c#L224-L256.

`ftCo_FireFlowerShoot_Anim` guards all work, including animation completion, with item_gobj!=NULL. It tests B3 before B4 and can perform both in one invocation: B3 calls `it_80292E64` (2/5→3), B4 calls `it_80292EAC` (3/4→5), then `ftCo_800CDE18` invokes `ftCommon_8007D92C` if no animation frames remain. The air Anim callback directly delegates. No held item means this path does not even run the completion helper. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L232-L249 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CDD.c#L59-L64.

Both IASA callbacks are empty. This proves no interruption logic in those callbacks, not global immobility or immunity to other transitions. Ground Phys forwards to `ftCo_800CDE54`→`ft_80084F3C`; air Phys forwards to `ftCo_800CDE74`→`ft_80084DB0`. Detailed movement equations remain delegated. Ground Coll supplies `ft_800CE5A0` to `ft_800841B8`, which synchronously calls it when `ft_800827A0` is false. Air Coll supplies `ft_800CE528` to `ft_80082C74`, which synchronously calls it when `ft_80081D0C` is true. The complete lower-level terrain predicates were not established here. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CE3.c#L251-L273, code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0CDD.c#L66-L74, code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L549-L556 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L1052-L1060.

## Invariants, ownership, boundaries, and uncertainties
All functions return void. The twelve state/entry/transition functions use Fighter_GObj*, while the damage and accessory definitions use HSD_GObj*. The parameter subjects refer to these incoming objects; no register ABI or compiled layout is inferred. The TU allocates or frees no fighter or held item and does not transfer ownership. It installs static function addresses in fighter callback fields, and stack vectors/scalars are passed to effects and emission helpers. Consumers must synchronously consume or copy those stack values; the full effect retention contract and callback-dispatch/clearing lifetime were not audited and remain unresolved. A non-null item is tested only at the outer entry to accessory/Anim processing, without kind checks or revalidation after every helper.

The modulo expressions require a valid nonzero interval; interval 1 requests the periodic calls on every attempt. No local validation protects zero, negative, or extreme intervals, counter overflow, or invalid common-data pointers. Countdown <=0 includes signed zero. Under ordinary IEEE comparison semantics NaN fails ordered threshold tests; positive infinity countdowns do not expire; x10 is not finite-checked, and very large finite values may cease changing under +1. A NaN x5B0 prevents both advancement and the final >= completion test. These are source-level boundary observations, not claims that shipped data contains exceptional values. Zero/nonfinite scale in the delegated position transform is likewise unguarded. Actual common-data values and engine floating-point compilation semantics remain unverified.

No compiled artifact was supplied for .sdata2. Literal use does not prove pool size, ordering, placement, or which loads refer to it. All three baseline section claims remain unresolved. The alternate union-member timer access also requires compiled layout evidence. Effect-number visual identities, exact periodic fighter-update semantics, throw-bit consumption implementation, full transition-mask semantics, and exact external physics behavior remain explicitly unresolved.
