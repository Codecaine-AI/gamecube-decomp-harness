## Scope and implementation
The owned C file defines four Master Hand Slap phase callbacks and one separate WalkShoot entry routine. The header declares all five as `void(HSD_GObj*)`. Both canonical and rendered files were read completely in inherited research; rendered substitutions were treated as hypotheses, not independent evidence. Lead review independently checked the owned implementation and the contradictory gameplay mapping's caller evidence.

### Slap lifecycle
- `ftMh_Slap_Anim` does nothing while animation frames remain; otherwise it forwards the same object to `ftMh_MS_389_80151018`. That cross-file routine selects `ftMh_MS_Wait2_1`, initializes its wait path, and stores a continuation callback and an attribute-derived target in fighter move storage. These writes outlive the Slap callback. [Callback](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMasterHand/ftmasterhandslap.c#L13-L18), [completion setup](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMasterHand/ftmasterhandwait12.c#L115-L138).
- `ftMh_Slap_IASA` retrieves the Fighter, queries its player slot type, and calls `ftBossLib_8015BD20` only when the result equals numeric zero. Other values skip that helper. This pass does not equate zero with a particular player category or adopt the rendered Crazy Hand helper name. [Evidence](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMasterHand/ftmasterhandslap.c#L20-L26).
- `ftMh_Slap_Phys` delegates to `ft_80085134`. Canonical callee evidence from inherited research verifies `self_vel.x = x6A4_transNOffset.z * facing_dir` and `self_vel.y = x6A4_transNOffset.y`; this helper does not write Z velocity, apply gravity, or transition state. `ftMh_Slap_Coll` is empty, which establishes only that this callback performs no collision work—not that the entire move lacks collision or hitboxes. [Callbacks](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMasterHand/ftmasterhandslap.c#L28-L33), [physics helper](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_084E.c#L120-L125).

### Separate WalkShoot entry
`ftMh_MS_349_80151CA8` changes to the canonical named state `ftMh_MS_WalkShoot` with arguments `(gobj, ftMh_MS_WalkShoot, 0, 0, 1, 0, 0)`, calls `ftAnim_8006EBA4`, assigns `cur_pos.y = da->x50.x`, and clears only `self_vel.x`. The source explicitly questions the attribute-component assignment; its intended meaning is not resolved here. The proposed name `ftMh_WalkShoot_Enter` is supported by this body, but is not a recovered original name. No numeric state identity is inferred from the original symbol's `349` suffix. [Evidence](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMasterHand/ftmasterhandslap.c#L35-L46).

The cross-file WalkLoop animation callback invokes this routine when target displacement length is less than `da->x4C`. Crucially, it does not return afterward: a floor-left-boundary check can enter WalkWait, and a later animation-completion check can reset WalkLoop during the same invocation. Thus entry into WalkShoot is not an unconditional guarantee of the final state after the caller returns. WalkShoot has its own callback quartet and the same animation-completion destination as Slap. [Caller](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMasterHand/ftmasterhandwalk.c#L102-L130), [WalkShoot callbacks](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMasterHand/ftmasterhandwalk.c#L19-L39).
