# Kirby SpecialS translation unit

The complete 212-line canonical and rendered forms of `src/melee/ft/kinds/ftKirby/ftkirbyspecials.c` were independently read, together with every owned subject/fact page and outgoing-link page. The librarian's account is substantially supported. This lead review preserves its uncertainties and additionally declines to retain claims whose wording exceeds the demonstrated behavior, notably universal cleanup safety, upward launch, visual enclosure, and upstream Inhale causation.

## Canonical identities and scope

The TU implements ground and air SpecialS entry, animation, physics and collision callbacks; a shared command-driven Hammer article callback; two article cleanup/notification helpers; and four SpecialN output/accessor helpers. The active table registers the respective SpecialS animation, physics and collision callbacks with NULL IASA slots: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirby.c#L507-L528. The constructor explicitly selects `It_Kind_Kirby_Hammer`, independently establishing the Hammer association: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itkirbyhammer.c#L50-L72.

Canonical names remain authoritative. `ftKb_SpecialAirLw_800F539C` and `ftKb_SpecialAirLw_800F5524` participate in the Hammer lifecycle despite their prefixes. Rendered `HammerDestroyed`, `ItemKirbyHammerSetup`, `ItemKirbyHammerRemove`, `GetPosition`, `GetStarCollisionBox`, and `SetupThrownKirbyVel` are descriptive hypotheses, not recovered original names. `GetStarJObj` is particularly uncertain because the canonical return type is `HSD_Joint*`, not a live `HSD_JObj*`. Rendered collision aliases cannot prove contact polarity.

## Article commands, ownership and callbacks

`fn_800F53AC` recognizes exactly command values 1 and 2. For 1 it computes a position using `FtPart_R3rdNa`, supplies the fighter object, position, part, ground-or-air value and facing direction to `it_802ADC54`, and assigns the nullable result to both `u.kb.hat.x0` and `x1984_heldItemSpec`. It consumes command 1 even when construction fails. Only success checks for a conflicting non-NULL `death2_cb`, reports `Other Dead_Proc Existence` and invokes `__assert` with filename `ftkirbyspecials.c`, line argument 0x66 and condition text `0` on conflict, then installs `ftKb_Init_800EE74C` and `ftKb_Init_800EE7B8` as death and damage callbacks. The effect helper chooses 0x497 exactly for `GA_Air`, otherwise 0x496, uses HipN and the facing-direction address, sets `x2219_b0`, and installs effect hitlag callbacks. Command 2 conditionally removes and clears the tracked article and consumes the command. Other values remain unchanged. The two command tests are independent `if` statements. There is no preexisting-item guard before creation, so repeated creation can overwrite a tracked reference. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L26-L87.

The constructor copies the supplied position into `spawn.prev_pos`, obtains `spawn.pos` separately, initializes zero velocity and parent references, and performs attachment/particle setup only on successful creation. Thus 'spawns at the supplied joint position' is an incomplete description. It does not retain the caller's local position address through the shown assignments. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itkirbyhammer.c#L30-L72.

`ftKb_SpecialAirLw_800F539C` only clears `u.kb.hat.x0`. The Hammer destruction callback invokes it for a non-NULL owner, without comparing the destroyed article against the owner's current tracked article. `ftKb_SpecialAirLw_800F5524` null-checks that field, calls `it_802ADC34`, and clears it after return. The wrapper forwards to `Item_8026A8EC`. Both installed Kirby lifecycle handlers call this cleanup helper but also clean other move resources, so they are not exclusive Hammer callbacks. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L31-L34; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L89-L96; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itkirbyhammer.c#L15-L28; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirby.c#L2580-L2601.

Sequential cleanup after successful return is a no-op once the field is NULL. This does not prove general reentrancy, alias safety, or fighter/item lifetime validity. Local cleanup does not explicitly clear `x1984_heldItemSpec`, accessory/death/damage callbacks, or effect state. Published function addresses have no stack lifetime, but engine contracts must establish reference and effect-argument lifetimes.

## Entries and action updates

Both entries clear `cmd_vars[0]`, request their respective SpecialS state with arguments `0, 0.0f, 1.0f, 0.0f, NULL`, call `ftAnim_8006EBA4`, and install `fn_800F53AC` as `accessory4_cb`. The aerial entry first assigns `specials_aerial_vertical_momentum` to `self_vel.y` only if `u.kb.x64` is false, then sets that flag. This is assignment, not addition, and there is no positivity or finite-value validation. Re-entry while the flag remains true skips that assignment. A universal once-per-airtime claim requires external reset auditing. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L98-L122.

Animation callbacks act only when `ftAnim_IsFramesRemaining` returns zero: ground calls `ft_8008A2BC`, air calls `ftCo_Fall_Enter`. Neither locally destroys the article. Detailed downstream neutral/Fall dispatch remains unresolved, rather than assumed from names. Physics callbacks unconditionally delegate to `ft_80084F3C` and `ft_80084EEC`. Ground physics selects character ground friction, multiplies it by `friction_when_above_walk_speed` only when `ABS(gr_vel) > walk_max_vel`, then calls ground friction and movement. Equality and unordered comparisons do not take the scaling branch. Stronger braking requires valid tuning and a multiplier greater than one. Air physics calls `ftCommon_Fall` with gravity and terminal velocity, then `ftCommon_ApplyFrictionAir`; no steering or fast-fall branch appears in that helper. Detailed numerical helper contracts remain unresolved. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L124-L147; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_084E.c#L33-L53.

Ground collision returns immediately for nonzero `ft_80082708`; otherwise it optionally removes the article, clears the reference and calls Fall, not aerial SpecialS. Air collision acts for nonzero `ft_80081D0C`: optional article cleanup, unconditional `x64=false`, and `ftCo_LandingFallSpecial_Enter(gobj, 0, specials_landing_lag)`. The queried helper updates collision/fighter positions and combines a map-query result with an overriding check; its GroundOrAir return names do not prove gameplay polarity. The landing callee optionally chooses HammerLanding; otherwise it supplies `(0.1F + fp->x2EC) / landing_lag` as animation rate. Zero, negative, infinite and NaN lag are not validated and do not guarantee finite normal recovery. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L149-L176; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L105-L123; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Landing.c#L103-L113.

## SpecialN outputs and cross-file consumers

`ftKb_SpecialN_800F5800(HSD_GObj*, Vec3*)` copies the complete fighter `cur_pos` into caller storage. `it_802F289C` passes the item's retained `grab_victim` and `&pos`; `it_802F2810` installs that accessory callback while selecting item state 1. The getter performs no allocation, null check or state transition. State index 1 does not independently establish a second Inhale capture phase, nor does the shown caller alone establish the retained object's complete gameplay provenance. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L178-L182; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itkirby_2F23.c#L133-L161.

`ftKb_SpecialN_800F5820` writes top, bottom, left.x, left.y, right.x and right.y from six Kirby attributes multiplied by one supplied scalar. Ordinary and copy-star initializers pass the thrower, the victim's persistent `thrownkirby.coll_box`, and the uniformly assigned accessory scale's X component. Terrain collision subsequently consumes the box. No sorting, absolute value, normalization or finite check occurs. Zero collapses finite coordinates; negative scale can reverse bounds; exceptional values propagate through multiplication, including invalid zero-times-infinity. The source writes six members but does not prove complete compiled object layout. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L184-L197; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_ThrownKirby.c#L72-L86; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_ThrownKirby.c#L99-L227.

`ftKb_SpecialN_800F5874(Vec2*)` reads Kirby's global ext_attr through an `ftCommonData*` view and copies `x9C_radians` and `xA0_radians`. The suffixes do not prove angles: the ordinary-star branch of `ftCo_800BE494` uses the output as vertical velocity and multiplied/oriented horizontal velocity; the copy-star branch bypasses it. A nonzero `mv.ca.specialhi.vel.y`, including NaN under ordinary C floating truth semantics, takes the multiplier branch without normalization. Otherwise existing horizontal velocity less than zero selects -1; zero, negative zero and unordered comparisons select +1. Neither a nonnegative X magnitude nor finite output is guaranteed. Ordinary recovery subsequently calls Fall when its timer is <=0; copy recovery bypasses that wait. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L199-L204; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_ThrownKirby.c#L262-L320.

`ftKb_SpecialN_800F5898` returns `M2C_FIELD(&ca->x48_items[0], HSD_Joint**, 0x10)`. The common star initializer passes that descriptor to `ftCommon_SetAccessory`, scales the live accessory and attaches it relative to YRotN after state selection and victim invisibility. The accessor itself does not allocate or mutate. The caller has MUST_MATCH versus HSD_JObjGetScale source branches for saving model scale; neither proves a compiled pointer-slot equivalence for this accessor. Exact visible enclosure and upstream swallow/copy-ability causation remain unproved. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftKirby/ftkirbyspecials.c#L206-L211; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_ThrownKirby.c#L99-L156; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_ThrownKirby.c#L212-L227.

## Dependencies, conventions and storage

The TU depends on Fighter/HSD payload conventions, Kirby attributes, global fighter data, motion/animation services, joint transforms, item construction/destruction, effects and hitlag callbacks, collision, landing/Fall, and diagnostics. Object/output arguments require valid storage; local article-null guards are not fighter-null guards. Source diagnostic arrays include writable `char[2] = "0"`; section membership, padding and complete `.data`, `.sdata`, `.sdata2` contents require compiled evidence. PAD_STACK is a matching convention, not verified object layout. No owned header or dox was assigned. The renderer reports one parse error and 22 substitutions; the final accessor and macros have parse uncertainty. None of those substitutions is independent semantic evidence.
