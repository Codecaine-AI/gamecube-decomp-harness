## Pool and lifetime
The source declares `gTRKMsgBufs` as three MessageBuffer entries, each with an 0x880-byte payload. Initialization clears occupancy but does not reset cursor, length or payload. Allocation scans from index zero, resets the first free slot's cursor and length while preserving bytes, marks it used, and returns its index and pointer. Exhaustion returns `kNoMessageBufferAvailable`, sets the output pointer to NULL, and leaves the output index untouched. Lookup neither claims a slot nor checks occupancy. Release silently ignores invalid indices, including the explicit -1 sentinel, and clears only occupancy for indices 0–2. Reset does not release ownership. These operations call mutex APIs, but the canonical mutex implementations simply return success; actual synchronization must not be inferred. Packet intake can transfer a buffer ID into an event. Request dispatch resolves that ID, handlers decode the request and may rebuild the same buffer as a reply, and event destruction releases the ID after dispatch. Packet classification can release a buffer earlier. These are source-level lifetime paths, not a guarantee that every exceptional caller path releases correctly. ## Cursor and transfer semantics
Seeking accepts offsets through the capacity boundary, extends length when needed, and does not initialize newly exposed bytes. Generic append copies the fitting prefix on overflow, advances the cursor, and replaces length with the resulting cursor; writing after a backward seek can therefore shorten the logical message. A zero-byte request returns immediately. Raw reads consume the available prefix on a short-read error and do not change length. These bounds calculations assume valid metadata; they do not validate arbitrary corrupted cursor/length combinations. [Seek and raw transfers](code://c302741689bd67c361cd7faadb221df3193992c3/src/MetroTRK/msgbuf.c#L90-L164).

The header's inline byte append is materially different from generic append: it increments length independently of the cursor. Consequently, byte-array append is not interchangeable with a generic byte-range append after repositioning. [Inline byte append](code://c302741689bd67c361cd7faadb221df3193992c3/src/MetroTRK/msgbuf.h#L59-L69).

## Typed serialization
Scalar 16-, 32- and 64-bit append helpers request big-endian representations and propagate partial-write errors. Scalar readers select direct destination storage when `gTRKBigEndian` is set; otherwise they read into temporary storage and reverse bytes only after success. A short direct read can modify a destination prefix. Array helpers stop on the first error, retain prior effects, and perform no iterations for nonpositive counts. The ui64 reader declares its temporary with `sizeof(data)`, where data is a pointer, while requesting `sizeof(*data)` bytes and indexing eight bytes. Its alternate-endian branch is unsafe wherever the pointer-sized temporary is smaller than the value; no compiled stack-layout or runtime manifestation is asserted.
