## Scope and interface
The complete owned TU is ftCo_Turn.c (190 lines) and ftCo_Turn.h (20 lines). The header declares all eleven functions and introduces no storage or implementation. The implementation supplies the common Turn input predicate, transition wrapper, parameterized initializer, Basic and Smash initializers, reversal helper, and Anim/IASA/Phys/Coll callbacks. The active motion table associates the four callbacks with the Turn entry, rather than this interpretation resting on an enum number alone (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftmotionstates.c#L332-L342). Header signatures are consistent with the definitions (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.h#L1-L20).

## Input and initialization
ftCo_800C97A8 is a read-only predicate: input.lstick[0].x * facing_dir <= p_ftCommonData->x34. Equality qualifies; unordered floating-point comparisons do not. It neither checks groundedness nor changes state. ftCo_Turn_CheckInput calls it, enters Basic on success, and returns true only on that branch. Its local Fighter pointer is otherwise unused. The reverse-input interpretation assumes the normal facing convention and configured threshold; this TU does not validate either (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L28-L47).

ftCo_Turn_Enter accepts gobj, msid, flags, arg3, frames_to_turn and anim_start. Before changing motion it clears has_turned, just_turned and x1C, records -facing_dir in facing_after, stores the requested countdown and copies arg3 into x8. It passes msid, flags, anim_start, 1.0F, 0.0F and NULL to Fighter_ChangeMotionState, then invokes ftAnim_8006EBA4. Basic obtains standing_turn_frames from co_attrs and selects ftCo_MS_Turn, Ft_MF_None, zero x8 and start frame zero. Smash performs equivalent initialization directly, but supplies a zero countdown and saves the original facing in x8. Entry itself does not explicitly negate facing_dir (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L49-L70; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L173-L189).

## Reversal and animation completion
ftCo_Turn_Anim_Inner decrements a strictly positive countdown by 1.0F and returns even if that subtraction reaches or crosses zero. Only a subsequent invocation that fails the positive test can set has_turned and just_turned and negate the current facing_dir. The guard makes this one-shot until reset. It negates current facing, not assigns facing_after; agreement requires no intervening persistent facing change. Zero, negative values, negative infinity and NaN bypass the positive branch under ordinary C floating-point comparisons. Positive infinity remains positive, and sufficiently large finite single-precision values can fail to change when subtracting one. For small representable positive counts, including fractional counts, reversal occurs after the decrementing invocations, not on the decrement-to-zero invocation. ftCo_Turn_Anim always runs the helper first, then calls ft_8008A2BC if ftAnim_IsFramesRemaining is false; animation exhaustion can therefore dispatch completion before a long countdown has produced reversal (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L72-L95).

## Interrupt ordering and button replay
IASA first ORs x1C into input.pressed_buttons when just_turned is set. Before reversal it negates facing_dir and checks, in exact order: ftCo_SpecialS_CheckInput, ftCo_800D68C0, ftCo_Attack100_CheckInput, ftCo_Catch_CheckInput, ftCo_AttackS4_CheckInput, ftCo_AttackHi4_CheckInput, ftCo_AttackLw4_CheckInput, ftCo_AttackS3_CheckInput, ftCo_AttackHi3_CheckInput, ftCo_AttackLw3_CheckInput and ftCo_Attack1_CheckInput. Each RETURN_IF ends processing on acceptance. In particular, early acceptance in this first group bypasses the second facing negation: restoration is not unconditional. If execution continues, it conditionally negates facing again and checks ftCo_80091A4C, ftCo_800DE9D8 and ftCo_Jump_CheckInput, also with early returns. Thus later checks are not all evaluated with prospective facing before reversal (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L97-L127).

The canonical symbol ftCo_Attack100_CheckInput must not be described as rapid attack in this chain: its active implementation tests a non-NULL ftData_SpecialHi callback and x686 == 0, then invokes that callback. Likewise ftCo_800D68C0 uses ftData_SpecialLw and x687 == 0. These optional callback branches are directly established, independently of rendered substitutions (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Attack100.c#L67-L101).

After all interrupt predicates fail, IASA calls fn_800C9C2C and ignores its boolean return. That helper latches facing_after into x8 only when facing-relative stick input is >= dash_smash_stick_threshold and the tilt timer is strictly < dash_smash_window. Failure preserves an earlier x8. Timing equality fails; strength equality passes. NaN in the strength calculation fails the comparison. IASA separately enters Dash with argument 0 when just_turned, scalar truth of x8, and the current facing_after-relative strength test all pass. x8 is not compared for directional equality and is not a boolean-only storage field. Both signed zeros are false; NaN is truthy under ordinary C scalar conversion, though the separate stick comparison must still succeed. The final Dash guard has no fresh timing test. Smash initializes a normally nonzero x8 without requiring this helper to succeed again (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L128-L171).

There is no return after ftCo_Dash_Enter. Execution continues to accumulate current A and B presses into x1C and conditionally clear just_turned. These final operations occur only on paths reaching the tail; early returns skip both accumulation and clearing. x1C is OR-accumulated rather than cleared after replay, and just_turned is not inherently a universally one-frame event. Dash entry changes motion and writes mv.co.dash fields before the remaining Turn accesses; the cross-state storage implications require layout/lifecycle verification, not an assumption that the Turn union remains semantically active (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L128-L148; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Dash.c#L49-L71).

## Physics, collision and consumers
Phys forwards gobj unchanged to ft_80084F3C. That helper obtains ground friction, multiplies it by friction_when_above_walk_speed only when ABS(gr_vel) > walk_max_vel, applies ground friction, then ground movement. Equality does not select the multiplier (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L150-L153; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_084E.c#L42-L53).

Coll forwards to ft_80083F88, which calls ftCo_Fall_Enter precisely when ft_80082708 returns GA_Ground. The latter synchronizes collision last/current positions, calls mpColl_8004B108, writes position back, and returns GA_Air for a true query result and GA_Ground otherwise. The enum names and local fall_off_ledge name do not justify reversing this actual predicate or asserting the physical meaning of the query (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Turn.c#L155-L158; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L392-L404; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L1027-L1033).

ftCo_Dash_CheckInput selects Smash for a strong, recent stick input whose product with facing_dir is strictly negative; otherwise its qualifying branch enters Dash directly. Dash IASA is an active caller of this checker. This establishes a dash/turn connection without claiming Smash is exclusively callable from an already active Dash (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Dash.c#L27-L46; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Dash.c#L103-L125). CargoTurn reuses the predicate and parameterized initializer with a cargo attribute-derived motion and delay, then separately changes the victim's state; its own animation uses differently named move-state members. HeavyTurn directly reuses ftCo_Turn_Anim_Inner (code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CargoTurn.c#L16-L50; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftDonkey/ftdonkeyheavyturn.c#L16-L22). No numerical motion-offset gameplay interpretation or compiled union-layout assertion is made.

## Conventions, ownership and uncertainties
All functions operate synchronously on a supplied fighter object; the owned code allocates/frees nothing, retains no pointer, installs no closure, and supplies NULL as the final motion-change argument. Valid gobj/user data, common data and move-state lifetime are preconditions, not checked here. The active table stores ordinary function callbacks. Precise scheduler ordering, transition-time callback replacement, motion-state preservation of initialized fields, and post-Dash union lifetime are not proved by this TU. Header address comments and parameter entity suffixes are not compiled ABI evidence: source parameter roles are known, but assigning floating parameters to literal r6/r7/r8 hardware registers is unresolved. PAD_STACK is a decompilation convention, not gameplay state.

Rendered ftCo_Turn_CheckInput_Inner for ftCo_800C97A8 and ftCo_Turn_CheckInput_Smash for fn_800C9C2C are plausible descriptive hypotheses, not recovered canonical names. The latter is an intent-latching helper, not a state-entry wrapper. Rendered external names do not prove semantics; the SpecialHi/SpecialLw distinction and physics behavior above were checked in canonical callees. Exact x34 configuration, original x8 name, animation helper internals, completion-dispatch destinations, compiled section contents, parameter ABI placement and move-state layout remain unresolved. Inline 0.0F/1.0F uses are visible, but no compiled artifact proves the asserted eight-byte .sdata2 pool.
