# Common Wait callback review

The owned C file defines four void fighter-object callbacks; the header declares those same four entry points. The Wait row registers them as animation, IASA, physics and collision callbacks. This is the ordinary grounded idle action, not an allocation or lifetime-management subsystem. ## Animation and exceptional paths

Anim reads Fighter.x2224_b2. A set flag calls ftCo_DownSpot_Enter; otherwise it passes the object and ft_data->x24 to ftCo_8008A7A8. This proves the flag's dispatch role, not its full gameplay meaning. The delegated routine only selects or replays an animation when no frames remain. A null wait table, or a held item on a fighter other than Fox or Mewtwo, selects replay of the current animation. Replay is a no-op when anim_id == -1.

The alternative draws HSD_Randi(100)+1 and searches cumulative table weights until a selection or the -1 terminator. Exhausting the table reaches the illegal-data assertion. Selection retries the current animation unless the current ID is 2 or 31; these numeric animation IDs are not assigned speculative state names. If only the current non-exempt animation is selectable, the retry can continue indefinitely. The code does not establish valid table termination, weight totals, index bounds or eventual selection for every character table.

For a selected ID other than -1, processing indexes animation/blend data, updates anim_id, installs the command-script reference and resets its loop count and timer. Assignment of animation flags and the ftAnim_8006EBE8 setup call are conditional on x590 != NULL; the script reset and ftAnim_8006EBA4 call are outside that condition. Thus 'animation advances' in retained family summaries means delegated processing, not unconditional mutation or guaranteed successful setup. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftwaitanim.c#L19-L105.

## Input priority and rendered names

IASA forwards the same fighter object through 21 ordered RETURN_IF checks, stopping on the first true result. The second check's canonical name, ftCo_Attack100_CheckInput, is misleading: its body dispatches ftData_SpecialHi, not rapid jab. The next two address-named checks dispatch neutral and down specials. Their rendered SpecialHi/SpecialN/SpecialLw names are independently supported by canonical bodies, rather than by substitution itself. The address-named squat check tests a strict downward-stick threshold and enters Squat. ## Physics, boundaries and exceptional floats

Phys calls ft_80084F3C before ftColl_8007AEE0. The first starts with ground_friction and applies the high-speed multiplier only when ABS(gr_vel) > walk_max_vel: equality does not activate it. ftCommon_ApplyFrictionGround clamps to -gr_vel when ABS(friction) > ABS(gr_vel); otherwise it negates friction when gr_vel > 0, then assigns xE4_ground_accel_1. It does not directly decrement gr_vel. Ground movement applies the surface multiplier only when it is strictly below one, then projects acceleration and current ground velocity along the floor normal into animation/self velocity, setting their z components to zero. The shared fighter update integrates and clears pending accelerations and animation velocity. The second Wait helper clears shield_hit.skip_update_pos; it does not itself update a shield position.

These helpers establish no finite or nonnegative input invariants. Ordinary passive deceleration assumes suitable attributes, velocity and surface data. Negative friction or multipliers can invalidate that interpretation; NaNs can bypass ordered comparisons and propagate through arithmetic, while infinities can propagate or produce invalid products. No universal finite-output, monotonic-deceleration or sanitization guarantee is inferred, nor is compiled exceptional-float behavior claimed. ## Collision, ownership and lifetime

Coll unconditionally delegates to ft_80084280, also used by Landing. That helper selects an alternate collision path for nonzero horizontal player-nudge velocity opposed to facing; otherwise it updates collision positions, stick input and facing, runs map collision and copies position back. A successful collision result returns; otherwise ftCo_8009A3C8 can consume the response, with Fall entry as the final fallback. The wrapper is unconditional, but Fall entry is not. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L1062-L1099; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Landing.c#L157-L160.

The callbacks borrow their object and require valid Fighter data; the animation branch additionally requires valid character data before passing the possibly null wait table. They neither allocate/free the object nor establish its lifetime. The delegated animation code stores a script-data reference in Fighter, so backing animation/script data must remain valid for subsequent consumption; these wrappers do not establish that lifetime. Physics likewise leaves pending data for another file's update rather than completing all integration locally. No binary section, register-allocation or compiled layout claim is made.
