## FallAerial collision is not a swing-specific falling phase
`ftCo_FallAerial_Coll` simply calls `ft_800831CC(gobj, ftCo_80096CC8, ft_80082B1C)`. The active common motion table registers it for FallAerial, alongside FallAerial animation/IASA/physics callbacks; source-file proximity does not make that state part of held-item swing attacks. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftswing.c#L21-L24 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftmotionstates.c#L486-L496.

The shared dispatcher synchronizes collision last/current positions, selects `mpColl_80047AC8` if ledge cooldown or `x2224_b2` is set and otherwise sets facing and calls `mpColl_80047E14`, then copies corrected position back. `ft_80081A00` can veto acceptance even after the collision query reports contact. Accepted contact invokes the supplied response synchronously; otherwise wall-jump checking precedes ledge-grab checking, with a successful wall-jump short-circuit. The predicate rejects line -1; other non-platform lines are accepted, while platforms require stick Y strictly greater than `p_ftCommonData->x25C`. The response calls `ft_8008A2BC` only when self vertical velocity is strictly greater than `ftCo_800D0EC8(fp)`; otherwise it enters basic landing.
