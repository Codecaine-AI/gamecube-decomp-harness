## Crazy Hand four-laser sequence

This unit implements three consecutive motion states, 0x166 → 0x167 → 0x168, with PaperCrush, Poke1 and Poke2 callback labels. The canonical registration table associates these callbacks with states 358–360; those labels are not evidence of three physical pokes. The concrete four-laser behavior supports the existing Laser Nail mapping. The rendered `_Enter` names remain convention-based hypotheses, not recovered symbols. [Registration](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhand.c#L238-L270).

### Entry and effect production

`fn_801582D8` enters 0x166 using flags 0 and floating arguments 0.0f, 1.0f, 0.0f, invokes `ftAnim_8006EBA4`, and initializes sound slots x38/x3C/x40 to -1. Opening animation exhaustion calls `ftCh_Init_801583E4`, which enters 0x167, performs animation setup, installs `fn_80158534` in accessory4_cb and sets cmd_vars[0] to 1. [Opening and active entry](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandpoke.c#L23-L62).

The accessory callback returns when cmd_vars[0] is zero. Otherwise it obtains positions from RLegJA, BustN, LHandN and L3rdNa, creates four It_Kind_MasterHand_Laser items with the owning object and facing direction, and stores the returned pointers in x28/x2C/x30/x34. It stores audio results for IDs 320004–320006, each called with volume 127 and pan 64, in x38/x3C/x40, then clears the latch. This is one execution per arming, not an unconditional guarantee of one execution per state: rearming would repeat setup and overwrite handles. No local allocation-failure recovery is shown. [Accessory body](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandpoke.c#L95-L126). The item constructor copies positions and attaches the created item's joint to the selected fighter joint. [Item creation](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itmasterhandlaser.c#L50-L79).

### Ordered cleanup and cross-file lifetime

When Poke1 animation expires, its callback first invokes `ftCh_Init_8015868C`. That enters 0x168, runs animation setup, keys off the three stored voices and resets their slots to -1. Only afterward does Poke1_Anim issue four item cleanup calls and clear the four fighter-held pointers. [Caller ordering](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandpoke.c#L64-L78), [ending entry](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandpoke.c#L128-L139), [audio key-off implementation](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/lb/lbaudio_ax.c#L201-L205).

Item cleanup is deferred: `it_802F046C` tolerates NULL and otherwise sets an item flag. The item animation callback handles joint detachment and returns true when it observes that flag. Importantly, animation exhaustion first calls an initializer that clears the flag, so destruction on the next update cannot be promised without scheduling evidence. [Request/reset/test ordering](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itmasterhandlaser.c#L87-L115).

These handles also have an external consumer: `ftCh_GrabUnk1_8015ADD0` clears the command latch and invokes cleanup that requests shutdown of the same four items, clears their pointers and keys off the same three voices before entering 0x181. Unlike the normal ending initializer, that path does not reset the sound slots to -1. Its reachability from every possible interruption is not established here. [Alternate cleanup](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandtaggrab.c#L22-L60).

### Completion and common callbacks

Poke2 animation exhaustion calls `ftCh_GrabUnk1_8015BC88`. This clears move flag x20, obtains a destination from attributes x18/x1C with z=0, installs `ftCh_Init_80156198` as a follow-up callback and initiates 0x184 positioning. The helper writes x2258=0x184 before testing it against 0x156, so the alternative branch is not taken in this shown path. The selected initializer preserves the current animation frame for an existing 0x184 value. Subsequent positioning physics and collision processing consume the destination and invoke the callback when distance becomes zero; the Poke2 callback does not itself finish that movement. [Final animation](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandpoke.c#L141-L146), [positioning setup](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandtagcancel.c#L109-L133), [frame preservation](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandtagcancel.c#L22-L33), [destination consumers](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCrazyHand/ftcrazyhandtagcancel.c#L89-L107).

All three IASA callbacks invoke `ftBossLib_8015BD20` only for Gm_PKind_Human; other slot kinds skip it. The pinned hook immediately returns. All three physics callbacks delegate to `ft_80085134`, which assigns self_vel.x from animation translation Z multiplied by facing direction and self_vel.y from translation Y. All three fighter collision callbacks are empty; this does not imply that the attached laser items lack collision behavior.
