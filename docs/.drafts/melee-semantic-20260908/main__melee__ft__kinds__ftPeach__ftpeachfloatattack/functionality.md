## Attack gate and entry
ftPe_8011BE80 resolves the attached Fighter, checks pressed A OR ftCo_800DF478(fp), then requires u.pe.x4 > 0. A successful request queries the common directional selector. The unsigned selected-ID-minus-65 test accepts exactly 65 and 66 in this selector's domain; 64 and 67 fail. Only this branch inspects the held item. A non-null item whose it_8026B30C result equals 3 dispatches ftCo_800CDDA0 and returns true. All other eligible requests call ftPe_8011BF34 and return true; failed guards return false without a local action-entry dispatch. There is no local Peach-kind, has_float, null-object, or allow_interrupt check. A short-circuited A test may skip ftCo_800DF478 at the outer gate, but the selector can call it again. See code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/ftpeachfloatattack.c#L24-L41.

The private entry helper queries the selector again, clears mv.pe.floatattack.x0, and calls ftCo_AttackAir_EnterFromMsid with selected ID plus ftCo_MS_CaptureDamageKoopa. That enum is an arithmetic offset here, not a Koopa-capture gameplay assertion. The common enum sequence establishes AttackAirN/F/B/Hi/Lw as 65–69 and CaptureDamageKoopa as 279; the Peach enum places its five Float attacks after Float and two FloatFall states, at 344–348. The active Peach table assigns the reviewed callback family to the five corresponding common aerial animations and move IDs. Thus directional mapping is supported by selector, arithmetic, enums, and active table together, not by numeric enum names alone. ## Animation and duration
Anim subtracts one from u.pe.x4 only when positive, then conditionally negates facing_dir through ftCheckThrowB3, then checks animation completion. While frames remain there is no local state-entry call. At completion nonzero floatattack.x0 enters Fall; zero calls ftPe_8011BB6C(gobj, false). That helper explicitly enters Float, clears has_float, zeroes vertical self velocity, and reloads duration only for a true argument. This return therefore does not replenish duration. See code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/ftpeachfloatattack.c#L51-L67 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/ftpeachfloat.c#L64-L90.

The duration field is source-declared float, not integer. One becomes zero; a positive fraction below one becomes negative rather than saturating. Zero, negative values, and NaN fail the positive guard. Under ordinary IEEE floating-point interpretation, positive infinity remains infinite and sufficiently large finite values may be unchanged by subtraction because of rounding. This is source-level boundary analysis, not proof that such values are reachable or that a particular target instruction/exception mode is used. Timer exhaustion prevents another attack but neither sets x0 nor immediately ends the active attack. A clear latch can request Float with an expired timer; Float's own Anim separately processes nonpositive duration. See code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/types.h#L12-L15.

## Continuation, interruption, and physics
IASA checks continuation before allow_interrupt. Continuation is main-stick y >= tap_jump_threshold OR held X/Y, including threshold equality; it is not exclusively a held-jump-button check. Failure writes true to x0; success does not directly clear it. Once interruptible, handlers run in order: ftCo_80095328(gobj, false), ftPe_8011BE80(gobj), ftCo_800CB870(gobj), advancing only on failure. A successful new Float attack clears x0 through entry, potentially during the same IASA invocation that set it. Therefore release is one-way only within an entry interval without re-entry, not an irreversible property of the fighter or motion ID. See code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/ftpeachfloatattack.c#L43-L82 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/ftpeachfloat.c#L20-L24.

The final delegate checks an exclusion, optionally delegates multijump, and otherwise invokes JumpAerial input processing. That processing has an alternate velocity path and a Peach-specific normal entry branch; not every invocation guarantees a jump. See code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_JumpAerial.c#L60-L122.

Phys forwards the same object to exactly one delegate: nonzero x0 selects ft_80084DB0, also used by common aerial attacks; zero selects ftPe_Float_Phys, which calls ftCommon_8007D268. The wrapper itself performs no timer update or explicit transition. See code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/ftpeachfloatattack.c#L84-L91, code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_AttackAir.c#L184-L187, and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftPeach/ftpeachfloat.c#L107-L110.

## Collision, callback lifetime, and landing
Coll unconditionally forwards gobj and ftCo_LandingAir_EnterWithLag to ft_80082C74. This delegate synchronously invokes the callback only when ft_80081D0C succeeds and does not store it. The landing callback checks cmd_vars[0] before switching on the current motion. Only ordinary AttackAir motions map to attack-specific landing states. Float-specific motions remain unmatched, so both command-flag branches reach basic landing. The unmatched path neither consumes the uninitialized lag local nor executes lag-reduction division or float-to-int conversion. This establishes the basic-landing mechanism associated with float canceling, but not an exact four-frame duration or complete auto-cancel equivalence.
