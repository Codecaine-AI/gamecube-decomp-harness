## Kirby copied-Yoshi attached-item handling

The implementation configures an existing `Item_GObj` supplied by Kirby's capture logic; it does not allocate an item. Setup stores the fighter in `atk_victim` and `grab_victim`, clears `xDD0_flag.b1`, installs `it_803F9490`, supplies article and fighter bone identifiers to the attachment helper, selects state 0 with flags 0, and invokes common setup helpers. The single table entry contains numeric motion value -1; this is distinct from the selected state index 0. Animation and collision callbacks return false, and physics is empty. These callbacks provide no autonomous lifetime or movement updates. [Source](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itkirbyyoshispecialn.c#L21-L57)

Teardown uses the stored fighter before clearing either reference. It invokes attachment cleanup, obtains the copied-Yoshi fighter joint and samples its position into `item->pos`, then calls two conditional player-bookkeeping helpers. Those helpers are not association-removal routines. Only the `destroy_type = 0` assignment depends on the boolean argument; both reference clears and the final cleanup/destruction calls occur regardless. There is no local null guard for the stored fighter. [Teardown](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itkirbyyoshispecialn.c#L59-L76), [bookkeeping helpers](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/it_279C.c#L1649-L1689)

Grounded and aerial capture callbacks pass `target_item_gobj` and Kirby to setup. Completion callbacks invoke teardown with false only when command variable 1 is nonzero and the target item exists; they then clear fighter-side references and consume that command. Creation of `It_Kind_Kirby_YoshiEggLay` is controlled independently by command variable 0, so destruction and creation are not necessarily adjacent events in time. Adjacent fighter-victim paths use different handling. The exact identity implied by historical 'tongue article' language remains uncertain: the inspected code establishes handling of a caller-supplied target item, not creation of a standalone tongue model.
