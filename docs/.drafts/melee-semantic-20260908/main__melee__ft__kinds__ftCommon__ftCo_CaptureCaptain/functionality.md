## Interface, naming, and evidence reconciliation
The complete owned C file defines `ftCo_8009CA0C(Fighter_GObj* gobj, Fighter_GObj* vic_gobj)` and four `void(Fighter_GObj*)` callbacks: `ftCo_CaptureCaptain_Anim`, `ftCo_CaptureCaptain_IASA`, `ftCo_CaptureCaptain_Phys`, and `ftCo_CaptureCaptain_Coll`. The guarded header includes fighter forward declarations and declares all five functions. `ftCo_CaptureCaptain_Enter` is a supported inferred alias, not the canonical symbol. The rendered cleanup, release-item, constraint, position-update, animation-advance, and velocity-reset names are hypotheses; only independently checked implementations support their semantics. The initialized local `u8 _[8]` is not subsequently used and does not establish compiled stack or section layout. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CaptureCaptain.c#L1-L53 and code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CaptureCaptain.h#L1-L13.

The prior librarian's central interpretation is independently supported: this is the captured-opponent side of Captain SpecialHi/Falcon Dive. Thus the first argument is the caught fighter and the second is its captor in this path, despite the canonical spelling `vic_gobj`. This conclusion comes from active callers, not numeric enum names. ## Entry data flow and dependencies
Entry reads both user_data pointers, calls `ftCommon_8007DB58`, `ftCo_8009750C`, and `ftCo_800DD168` on the first object in that order, stores the second object in both `victim_gobj` and `x1A5C`, clears `x221B_b5`, and assigns `facing_dir = -vic_fp->facing_dir`. Exactly `ground_or_air == GA_Air` calls `ftCo_800DB368(vic_fp, fp)` and clears `x221B_b7`; every other value sets that bit. Describing the else branch as grounded is a normal-state convention, not an exact GA_Ground test.

It requests `Fighter_ChangeMotionState(gobj, ftCo_MS_CaptureCaptain, Ft_MF_None, 0, 1, 0, fp->victim_gobj)`. The declaration identifies the float arguments as animation start, speed, and blend. The final pointer is forwarded exactly; its animation-source interpretation is not proved by the declaration. After the transition, entry tests the current `x221B_b7`, installing `ftCo_800DB464` as `accessory1_cb` only when clear. It then calls `ftCommon_8007E2F4(fp, 0x1FF)`, `ftAnim_8006EBA4(gobj)`, and `ftCommon_8007E2FC(gobj)`. The first common helper assigns its s16 argument to `x1A6A`; 511 fits and the helper performs assignment, not a bitwise mask operation. The last helper zeroes both ground accelerations, animation velocity, ground velocity, self velocity, ground/vector knockback velocities, ground/vector attacker-shield knockback fields, and `xD4_unk_vel`. Detailed effects of the first three entry helpers and the animation helper remain unresolved rather than inferred from rendered aliases. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CaptureCaptain.c#L14-L39; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/fighter.h#L44-L48; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftcommon.c#L906-L939.

Dependencies are the fighter object/data and motion-state infrastructure, common fighter setup helpers, capture-pulled joint helpers, animation processing, and fighter/map collision processing. The C file includes its own header, Runtime platform definitions, Attack100/Lift/Throw headers, fighter, collision, animation, common, and fighter types headers. No local allocation, free, ownership-transfer protocol, timer, or data-table definition is present.

## Optional joint setup, deferred movement, and lifetime
`ftCo_800DB368` obtains the captor's TransN2 joint before checking `x2226_b2`. When that bit is clear it obtains the captured fighter's XRotN joint, passes an all-zero quaternion to `ftParts_JObjSetRotation`, saves translation in `x2174`, calls `lb_8000C1C0(jobj, constraint)`, and sets the bit. An already-set bit skips that guarded setup but not the initial captor-joint lookup. `ftCo_800DB464` obtains XRotN position through `lb_8000B1CC`, adds `facing_dir * (x1A70.z * x34_scale.y)` to x and `x1A70.y * x34_scale.y` to y, forces z to zero, and stores `cur_pos`. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CapturePulled.c#L334-L367.

The accessory callback is a function pointer, not a closure referencing the entry stack. Accessory dispatch invokes it with the fighter object and then updates root-joint translation. The checked motion-state callback-reset block clears `accessory1_cb`, consistent with installing it after the transition. This does not prove clearing on every exceptional transition or destruction path. Raw partner pointers are stored without local retention, validation, or detachment. `x1A5C` also participates in recursive hitlag-related processing and cannot be reduced to an animation-source alias. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/fighter.c#L1370-L1389; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/fighter.c#L2540-L2548; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/fighter.c#L2748-L2772.

## Callback behavior and external consumers
The active motion table binds this exact Anim/IASA/Phys/Coll suite with CaptureCaptain submotion, capture flags, and `ftCamera_UpdateCameraBox`. Anim, IASA, and Phys have completely empty bodies: no argument reads, calls, writes, guards, timers, input tests, movement, or transitions. These no-op properties are function-scoped, not guarantees that all engine movement or input processing is suppressed. Coll resolves the Fighter and forwards the unchanged object to `ft_80083B68` only when `x2226_b2` is clear; when set it does no collision-helper work. The wrapper calls `ft_80082578`, which transfers position through collision data, calls `mpColl_800477E0` and `ft_80081A00`, and returns a floor-contact result ignored by the wrapper. The owned Coll body has no explicit transition; downstream side effects are not excluded. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftmotionstates.c#L3159-L3169; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CaptureCaptain.c#L41-L52; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L935-L939; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L347-L365.

## Boundaries and explicit uncertainties
Entry and Coll require valid fighter objects and data, without local null, identity, kind, alias, or lifetime checks. The empty callbacks themselves do not dereference even a null argument. Entry has no local early return, conditional on valid inputs and returning callees. Facing is arithmetic negation, not normalization: zero, nonunit values, infinities, and NaNs receive no explicit handling. Accessory arithmetic likewise has no exceptional-float guards. Exact compiled signed-zero, NaN-payload, and floating-point-exception behavior is unproved. All .sdata2 contents, extent, order, permissions, placement, and relocation-use claims remain unresolved without compiled evidence; source literals and address comments cannot prove them. Full partner detachment/destruction safety, final motion-state pointer semantics, global input/movement suppression, and complete damaging-release behavior remain unresolved.
