## Samus Bomb item lifecycle

The canonical implementation defines four numeric item motion states. Entries 0–2 use animation selector 0 and provide animation, physics and collision callbacks; entry 3 uses animation selector 1 and has no physics or collision callbacks. These are source-level observations, not compiled section-layout claims. [Source](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itsamusbomb.c#L20-L28)

### Creation and ownership
Samus's fighter accessory callback checks its throw event, derives a TopN-relative placement vector with facing-adjusted X offset, calls the Bomb constructor, and clears the accessory callback regardless of allocation success. The constructor requests `It_Kind_Samus_Bomb`, copies the supplied position into `prev_pos` with Z flattened, obtains `si.pos` through a separate helper, and initializes both parent references. Failed allocation returns NULL. Successful allocation runs Bomb initialization and the debug association hook. Initialization replaces the initially zero Y velocity with common attribute `x18`, clears command variable 2, saves the generic owner in Bomb-specific storage, initializes life timers from special attribute `x0`, and selects state 1. ### Live states and terrain
State 0 performs shared fuse processing and has an intentionally empty item-specific physics callback. Its collision helper updates position and floor index; loss of support invokes the state-1 transition. Importantly, the supported-floor path also calls `Item_8026ADC0` when `it_80277544(gobj) != 0` and `!ip->xDCD_flag.b3`. The Bomb wrapper's false return must not be interpreted as proving that delegated collision processing has no other effects. [Ground callback](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itsamusbomb.c#L104-L121) [Shared helper](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/itgroundcoll.c#L44-L70)

State 1 runs fuse processing followed by orientation processing, forwards common fall-speed attributes to the falling-physics helper, and supplies state 0 as its qualifying-landing callback. The common collision helper resolves contacts and invokes that callback only after its floor and additional landing guards pass. State 2 is selected by `EnteredAir`; it also runs fuse/orientation processing, but its physics limits the XY magnitude of `x7C`, not `x40_vel`. Its collision helper immediately selects state 1 when support is absent; with support, state 0 is selected only when the helper's `x1F`/`xD5C` guard permits it. [States 1–2](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itsamusbomb.c#L123-L195) [Landing guards](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/itgroundcoll.c#L507-L526) [State-2 routing](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/itgroundcoll.c#L750-L778)

The live fuse applies the model operation at or below special threshold `x4`, then checks expiration before decrementing. A timer of 1 becomes 0 on this update and detonates on the next. Orientation processing uses the exact guard `!(ABS(vx) < 0.0001f)` and sets Y rotation to zero for facing +1 or π otherwise. States 1 and 2 still execute this processing after preprocessing has entered explosion state; there is no intervening early return. The local square-root helper performs four reciprocal-square-root refinements for positive inputs and returns other inputs unchanged. Limiting uses a strict greater-than comparison followed by XY normalization and scaling. Nonnegative configured limits and ordinary finite inputs underlie the usual speed-cap interpretation. ### Detonation and interactions
Damage dealt, clank and shield hit invoke explosion setup only when `msid != 3`, then return false. Shield bounce independently forwards the shared bounce helper's result. Reflection first calls its shared helper, then replaces a negative Y velocity with `-y * xC70`; zero and positive values are untouched locally. Reflection always clears the custom saved owner. [Interaction callbacks](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itsamusbomb.c#L197-L244)

Explosion setup selects state 3 with animation updating, sets frame speed to 1, runs six shared setup helpers, installs the accessory callback, and arms its one-shot flag. The state-3 animation callback delegates to a timer helper that decrements before testing `<= 0`, unlike the live fuse. The item dispatcher removes the item when its animation callback returns true. [Explosion setup](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itsamusbomb.c#L246-L265) [Timer](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/it_2725.c#L1429-L1450) [Dispatcher](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/item.c#L1280-L1290)

The accessory consumes its flag before checking the owner or overlap. Missing ownership, failed overlap and fighter-side rejection therefore are not retried by subsequent accessory calls. Canonical fighter code checks hurt capsules and conditionally computes an angle-derived launch and enters fighter state `0x156`; this is distinct from item state 3. Reference invalidation delegates equality-based generic reference cleanup, then unconditionally clears the custom owner—even when the departing object is not that saved owner. The outer item loop separately decides flagged destruction. Numeric-state entry names remain conservative and are not renamed merely for stylistic consistency. Existing knowledge is explicitly retained in the checkpoint ledger; compiled pool/layout attributions remain unresolved rather than being inferred from source literals.
