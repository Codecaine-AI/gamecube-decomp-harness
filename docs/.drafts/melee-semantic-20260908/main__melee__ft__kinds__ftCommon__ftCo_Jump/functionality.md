# ftCo_Jump translation unit

## Scope and naming
The owned implementation is `src/melee/ft/kinds/ftCommon/ftCo_Jump.c` (212 lines), with its 20-line declaration header. It contains eleven externally declared functions: a read-only jump-source classifier, three state-changing input predicates, a shared launch initializer, ordinary jump entry, and Anim/IASA/Phys/Coll lifecycle callbacks (including a reusable inner physics helper). The header declares all eleven functions and contains no implementation or storage definitions. Canonical names remain authoritative. `ftCo_Jump_CheckInputFromGuard` for `ftCo_800CB024` and `ftCo_Jump_InitVelocity` for `ftCo_800CB110` are useful descriptive hypotheses, not recovered original names. The former is supported by active Guard and GuardOff callers; it must not imply exclusive use from active Guard. The rendered views parsed successfully, but their renamed external callees are not independent evidence. ## Input and startup
`ftCo_Jump_GetInput` resolves the Fighter and returns `JumpInput_LStick` if left-stick Y is >= `tap_jump_threshold` AND the vertical tilt timer is < `tap_jump_window`. Equality passes the stick threshold and fails the timer limit. Otherwise a newly pressed X/Y bit returns `JumpInput_XY`; otherwise it returns `JumpInput_None`. Simultaneously qualifying stick and buttons select stick. It neither clears input bits nor enters a state. NaN stick Y or threshold does not pass the ordered comparison under ordinary IEEE comparison semantics; the button fallback remains available. This routine does not itself verify grounded status. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L30-L44]

`ftCo_Jump_CheckInput` first tests `ftCo_800C5240` and exclusively returns `ftCo_800C5A50` on that branch. Canonical HammerWait code proves that the first predicate checks a non-null held item of kind `It_Kind_Hammer`; HammerJump code obtains the ordinary jump source and dispatches accepted input to `ftCo_800C5B88`. Outside that branch a nonzero classified source is passed unchanged to `ftCo_KneeBend_Enter`, followed by true; rejection returns false. `fn_800CAF78` follows the same Hammer-first scheme but uses `relaxed_tap_jump_threshold` for its ordinary left-stick branch. No actual numerical relationship between the relaxed and ordinary thresholds was established. Its Hammer branch still uses the ordinary classifier, not the relaxed threshold. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L46-L84; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_HammerWait.c#L139-L146; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_HammerJump.c#L15-L23]

`ftCo_800CB024` first attempts `ftCo_Jump_CheckInput`; only if that returns false does it call `ftCo_800DF910` and enter KneeBend with `JumpInput_CStick` on success. The latter predicate checks C-stick Y >= the ordinary tap-jump threshold without a tilt-timer condition. Notably, a failed Hammer jump attempt does not exclude this outer C-stick fallback. Active Guard and GuardOff invoke this predicate. KneeBend stores the initiating source, clears `is_short_hop`, enters its startup state, later checks release of the corresponding source, and can accept the named up-smash input checker during startup. Completion occurs at the startup-time boundary OR animation exhaustion and selects ItemScrew or ordinary Jump entry. The precise compiled storage correspondence between `kneebend.is_short_hop` and `jump.x0` was not established in this pass and is not asserted as a proved object-layout fact. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L86-L99; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_0DF1.c#L209-L215; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Guard.c#L539-L548; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Guard.c#L602-L618; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_KneeBend.c#L19-L66]

## Launch initialization and entry
`ftCo_800CB110(gobj, arg1, jump_mul)` clears `jump.x4`, stores the multiplier, scales existing horizontal self velocity by `ground_to_air_jump_momentum_multiplier * jump_mul`, executes an intermediate `self_vel.y *= x438`, and zeros depth velocity. It then adds `jump_mul * (stickX * jump_h_initial_velocity)` to the scaled horizontal velocity. Its signed cap is implemented literally as `if (ABS(h_vel) > jump_h_max_velocity * jump_mul)`, choosing the negative or positive cap according to `h_vel < 0`. Equality is unchanged. `jump.x0` chooses `hop_v_initial_velocity` rather than `jump_v_initial_velocity`; either is multiplied by `jump_mul` and assigned to Y. Thus the earlier x438-scaled Y is overwritten, not added to the final launch. The initializer does not change motion state or set `jump.x0`. It sets the tilt timer to 0xFE. `arg1` gates the complete audio block: the configured x10 SFX is requested first, and the additional 0x11A request requires non-null `x197C`. The gameplay identity of x197C and of that additional sound remains unknown. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L101-L151]

The initializer performs no validation of scale, attributes, or floating-point inputs. A symmetric bounded-speed interpretation requires a nonnegative finite cap and suitable finite arithmetic. Negative caps can reverse the expected result; NaN comparisons can bypass clamping; infinite products, including zero times infinity, can create infinities or NaNs. A zero multiplier produces zero launch components only for suitable finite operands and is not a general sanitization guarantee. Exact target floating-point exception/rounding behavior requires compiled/runtime evidence. The timer assignment only blocks subsequent `< window` tests when the configured window does not exceed 0xFE; unconditional repeat-input suppression is too strong without configuration evidence.

`ftCo_Jump_Enter` first calls `ftCommon_8007D5D4`, which sets airborne status, clears ground velocity and selected depth/animation state, records one jump used, and locks the ECB for 10. It chooses JumpF when `stickX * facing_dir > -x78`, otherwise JumpB; equality and unordered comparison choose JumpB. It enters the selected state with flags None, frame 0, rate 1, zero final float, and NULL auxiliary object, initializes velocity with true and 1.0F, then sets `x2227_b0`. The active motion table assigns the same four owned callbacks to JumpF and JumpB, with their respective submotions; this is table/caller evidence, not a numerical-enum inference. `x2227_b0` is also read by common airborne bookkeeping and cleared by grounded conversion; no stronger descriptive name is assigned here. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L153-L165; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftcommon.c#L515-L557; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftmotionstates.c#L409-L430]

The initializer is shared: ItemScrew enters its own state and passes false plus x800; HammerJump enters its own state and passes false plus unity. ItemScrew also reuses Jump IASA and the inner physics helper; HammerJump reuses the inner physics helper. These callers disprove any interpretation that the initializer exclusively belongs to ordinary Jump entry. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_ItemScrew.c#L21-L46; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_HammerJump.c#L25-L48]

## Lifecycle and callback ordering
Anim calls `ftCo_Fall_Enter` only when no animation frames remain. It is not an apex/vertical-speed test. Fall entry can route Master Hand, Crazy Hand, x2224_b2, or held-Hammer cases rather than always selecting ordinary Fall; its ordinary path preserves fast fall, clamps air drift, initializes fall-local state, and conditionally performs airborne conversion. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L167-L172; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Fall.c#L31-L71]

IASA tests, in exact priority order: `ftCo_SpecialAir_CheckInput`; `ftCo_80095328(gobj,NULL)`; `ftCo_800D7100`; `ftCo_800C3B10`; `ftCo_80099A58`; `ftCo_AttackAir_CheckItemThrowInput`; `ftCo_800D705C`; x4-gated `ftCo_800CEE70`; x4-gated `ftPe_8011BA54`; `ftCo_800CB870`; an unconditional return if x4 is clear; finally `ftPe_8011BAD8`. A true result terminates processing. x4 is read at each guard rather than cached once. The aerial-jump candidate is not x4-gated by this caller. Detailed gameplay meanings of the numeric external handlers remain hypotheses unless independently verified by their owners; this review proves the ordering and gating, not all rendered aliases. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L174-L190]

The public Phys callback only forwards to `ftCo_Jump_Phys_Inner`. When x4 is false the inner function sets it true and returns without a downstream physics call. Otherwise it calls `ft_80084DB0`. That helper checks fast fall, applies fast-fall speed or gravity capped at terminal velocity, then runs `ftCommon_8007D268`. This is one skipped invocation after each reset, not a proved scheduler-wide claim that every fighter experiences exactly one whole frame without any physics. [code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Jump.c#L192-L206; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_081B.c#L1363-L1375; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftcommon.c#L462-L507]

Coll forwards the object and two function pointers to `ft_800835B0`. Its shared query synchronizes Fighter and CollData positions, selects a query according to ledge cooldown/x2224_b2, and normally supplies facing direction; an `ft_80081A00` result can invalidate the query result. Accepted contact calls `ft_80082B1C` and returns; otherwise wall-jump, ledge-grab, and ceiling-stop candidates run in that order. `ftCo_80096CC8` rejects line -1, accepts non-platform lines, and accepts platform lines only for stick Y > x25C (equality and NaN reject the platform branch). `ft_80082B1C` calls `ft_8008A2BC` when Y velocity is strictly above `ftCo_800D0EC8(fp)`, otherwise basic landing; equality/unordered comparison takes basic landing. Ceiling contact can enter StopCeil and clear Y/Z velocity. The response callback is invoked synchronously in the examined dispatcher and is not stored there. The predicate is forwarded to lower stage-query code; its deeper retention/lifetime behavior was not proved. ## Ownership, interfaces, and uncertainties
All object parameters are borrowed Fighter_GObj pointers; the TU neither allocates, frees, nor transfers ownership. Functions assume a valid object/Fighter and initialized common data; enabled audio additionally assumes valid fighter-data/SFX pointers. Only the explicit held-item and x197C optional branches are null-checked. Callback functions have static program lifetime; the owned TU creates no closure or stack-backed callback context. Source signatures identify eleven object parameters, the Boolean audio argument, and the floating multiplier. The baseline parameter locators are reviewed, but their machine-register interpretation—especially the float's `#r5` label—is not independently validated as an ABI claim. No parameter fact is written on that basis. Literal uses prove zero/unity source expressions, not .sdata2 size, ordering, alignment, or placement. All three .sdata2 facts remain unresolved without compiled evidence. Other outstanding questions are the compiled KneeBend/Jump state overlay, x197C/0x11A meaning, complete external numeric-handler semantics, scheduler-level timing, lower collision predicate retention, and target exceptional-float behavior.
