## Gate and entry
`ftCo_8009B818` forwards the original object to `ftCo_800C97A8`; success calls `ftCo_8009B860` and returns true, otherwise it returns false. It performs no direct field accesses. The predicate is `lstick[0].x * facing_dir <= p_ftCommonData->x34`: equality accepts, and an unordered comparison rejects under ordinary floating comparison semantics. The actual threshold sign and input validation range are not established. CargoWait calls the gate after `ftCo_8009BF3C`, `ftCo_8009BB1C`, and `ftCo_8009C4F8`, and before `ftCo_8009B67C`. The third handler's platform-drop gloss is not independently established here. ## Animation and boundaries
Anim first tests `mv.co.walk.fast_anim_frame > 0`. If true it subtracts one, without clamping or reversing during that invocation. Otherwise, an unset `mv.co.cargoturn.x0` causes a fresh victim lookup, sets the guard, negates the carrier's current facing, and copies that result to the victim. It does not use Turn's saved `facing_after`. The guard prevents repetition only while it remains set. Zero, negative values, and unordered values reach the guard branch. A positive fractional timer can become negative and reverse only on a later invocation. For a positive integral N that decrements exactly, reversal first becomes eligible on invocation N+1. Positive infinity and sufficiently large finite values can fail to progress under subtraction. Negation does not normalize invalid facing values: zero, infinity, or NaN are not repaired.

The separate animation-completion test runs after either update path. If `ftAnim_IsFramesRemaining` is false, `ftCo_8009B518` is called even if the timer was positive and no reversal occurred. Reversal before completion is therefore not guaranteed. That completion helper changes the carrier to its motion base, then calls the Shouldered helper with numeric 266. The CargoWait table and implementation establish the carrier's wait role; 266 is not interpreted solely from its numeric value. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CargoTurn.c#L35-L51; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CargoWait.c#L29-L42; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftDonkey/ftdonkey.c#L151-L161.

Turn entry accesses `mv.co.turn`, while CargoTurn animation accesses `mv.co.walk` and `mv.co.cargoturn`. The intended timer/guard correspondence is plausible, but exact compiled overlap and the initialization bridge remain unresolved. No source-level comparison or literal use proves `.sdata2` bytes, ordering, size, ownership, or loads.

## Interrupts
IASA attempts `ftCo_8009BF3C` before `ftCo_8009BB1C`, stopping on success, with no local timer gate or fallback transition. The first handler checks canonical `HSD_PAD_AB`. Horizontal magnitude at or above `x98` takes priority; positive facing-relative x selects base +10, otherwise base +11. If the horizontal test fails, y at or above the upper threshold selects base +12, otherwise y at or below the lower threshold selects base +13. No qualifying selection leaves the current motion unchanged, and entry occurs only when the selected motion differs. Unordered comparisons follow the corresponding false paths; there is no local sanitization. Throw entry has an airborne variation using an additional motion offset and different flags, and updates the victim through a thrown-state helper. The active Donkey table binds these neighboring throw motions to cargo-throw callbacks, supporting directional cargo-throw semantics without relying on numeric names. The specific attack/grab gloss for `HSD_PAD_AB` is unproved here.

The second handler consumes nonzero `ftCo_Jump_GetInput` and calls `ftCo_8009B9C8`, which stores input and startup lag, changes to base +5, freezes animation, and requests ShoulderedWait for the victim. CargoKneebend is actively bound in the Donkey table. This proves a jump-sequence entry, not an extra-jump-count guarantee. ## Physics, collision, and lifetime
Phys unconditionally forwards to `ft_80084F3C`. This reads ground friction and multiplies it by `friction_when_above_walk_speed` only when absolute ground velocity is strictly above walk maximum; equality does not scale it. An unordered comparison does not enter the scaling branch. It then applies ground friction and ground movement. Multiplication is proved, but a universally increasing factor is not. Phys has no local timer, facing write, or transition. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_CargoTurn.c#L59-L62; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ft_084E.c#L42-L53.

That helper invokes the callback synchronously only when `ft_80082708` returns false, and does not store it. The active table confirms the CargoFall callback binding.
