# ftCo_Barrel translation unit

## Scope and identity
This unit implements the fighter side of item-form Barrel Cannon occupancy and launch. The owned implementation is 130 lines and its public header is 18 lines. The header exports nine functions; fn_800C9290 has internal linkage through its static forward declaration. All functions return void. Canonical symbols remain authoritative: ftCo_800C92E4 is the actual exported name; ftCo_Barrel_Launch is a supported descriptive hypothesis, not a recovered symbol. Rendered aliases for external helpers are not independent evidence.

The active motion-state table installs ftCo_Barrel_Anim, ftCo_Barrel_IASA, ftCo_Barrel_Phys, and ftCo_Barrel_Coll together with ftCamera_UpdateCameraBox. TaruCann registers ftCo_Barrel_Enter as an item interaction callback when its occupant field is empty. This establishes the item-form mapping without borrowing the stage-barrel mechanics of ftCo_BarrelWait. ## Occupancy callbacks and boundaries
ftCo_Barrel_Anim decrements x0 only when nonzero and calls it_80295F38(x8) only if that decrement produces zero. Initial zero disables this automatic request; initial one fires on that invocation. For positive integral values the request occurs after that many evaluations, not necessarily that many wall-clock frames. Nonnegativity is not enforced by this unit, so a universal nonnegative-countdown invariant is unsupported.

ftCo_Barrel_IASA first decrements nonzero x4, then tests the resulting value for zero and pressed_buttons & HSD_PAD_AB. Thus x4=1 permits firing on the same evaluation that decrements it to zero; x4=0 permits immediate input testing. The input is pressed_buttons, not merely a held-button condition. There is no local latch preventing another request on another qualifying invocation. Both callbacks delegate synchronously to the item firing operation. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Barrel.c#L61-L84.

ftCo_Barrel_Take_Dmg_Cb forwards the stored item to it_80295F38 without a timer or input guard. ftCo_Barrel_Death2_Cb calls that damage callback exactly once with the same fighter argument. it_80295F38 tolerates a null item, but entry accessors, positional synchronization, and owner lookup do not establish equivalent null safety. Fighter arguments must be valid for all dereferencing routines; Phys and Coll are empty and do not dereference their arguments. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Barrel.c#L23-L26; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Barrel.c#L54-L95; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/ittarucann.c#L78-L111.

ftCo_Barrel_Phys and ftCo_Barrel_Coll are invariant no-ops. This proves absence of work in these callbacks, not absence of every engine-wide physics/collision operation. ftCo_Barrel_Accessory1_Cb passes x8 and &cur_pos to it_8026C334. That helper writes x=item.pos.x+0.0f, y=item.pos.y+ECB.bottom.y, z=item.pos.z+0.0f. The additions by zero should not be silently replaced by bit-preserving copies for exceptional-float or signed-zero analysis. ## Launch, geometry, and damage transition
ftCo_800C92E4 receives the occupant Fighter_GObj, a requested launch Vec3, a cannon-position Vec3, a lbColl_80008D30_arg1 descriptor, and a float angle. Its item caller constructs a point eight units along the cannon direction, derives hit parameters from special attributes, and converts radians to degrees. The fighter routine computes cur_pos.x/y=(arg1.x/y+root translation.x/y)-ftLib_800866DC output.x/y, forces cur_pos.z=0.0F, calls mpColl_80043680(&coll_data,arg2), converts arg3 into a stack SmallerHitCapsule through a HitCapsule cast, and applies ftCo_Barrel_ApplyKnockback. It then invokes ftColl_800787B4 with the stored item, installs fn_800C9290 in x21EC, and calls ftCo_8008DCE0(gobj,0x5B,0.0F). Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Barrel.c#L106-L129; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/ittarucann.c#L78-L109.

The knockback inline adds 360 once if the angle is negative, then preserves it for facing_dir<0 or uses 180-angle otherwise. It computes kb_applied through ftColl_80079EA8 and records angle, facing, hurtbox index zero, current collision position, and hit element. This is not general modulo normalization. Zero facing follows the nonnegative-facing branch; NaN comparisons also fail their less-than tests. Direct launch inputs are not checked for finite values, valid pointers, or aliasing. The item caller's normalization loops can fail to terminate for infinities or sufficiently large floats whose subtraction/addition cannot progress; NaN bypasses ordered comparisons. Exact platform exceptional-float results remain unproved. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/inlines.h#L40-L53; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/ittarucann.c#L97-L108.

The third argument of ftCo_8008DCE0 is a facing override, not a starting frame. Zero means no override. Its second argument overrides the selected motion state, but a subsequent sufficiently strong Ice-element branch can select 0x5A instead. The damage helper itself passes starting frame zero and speed one to Fighter_ChangeMotionState. Accordingly this TU requests state 0x5B, but does not guarantee it in every parameter configuration. No gameplay label is assigned to 0x5B or 0x5A solely from numeric names. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Damage.c#L419-L447.

## Attribution and callback lifetime
fn_800C9290 obtains Item.owner through itGetOwner(x8). It calls ftColl_8007B8CC only if ftLib_80086960 confirms a non-null fighter-class object. The helper writes the launched fighter's thrown-hitbox owner, team attribution, and grabber_unk1 player ID from that owner. Null or non-fighter owners leave these fields unchanged; a null stored item is not protected by the owner classifier. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_Barrel.c#L97-L104; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/it_26B1.c#L710-L714; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftlib.c#L427-L434; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftcoll.c#L3391-L3397.

The damage helper performs that change synchronously; Fighter_ChangeMotionState invokes x21EC before clearing accessory1_cb, take_dmg_cb, and death2_cb later in its setup. TaruCann clears its occupant after the fighter launch returns. The item therefore remains needed through the attribution callback. No stack hit-capsule pointer is explicitly stored by this TU; a complete proof of callee non-retention and SmallerHitCapsule binary compatibility is not supplied.
