# Fighter item pickup

The single-item predicate checks grabbability, compatibility and strict 2D overlap. The item grab point includes its facing-adjusted local offset; fighter light regions differ on ground and in air, while heavy candidates always use the ground-heavy region. Existing held items permit only the helper's healing/coin allowlist. The finder adds a CPU-mode exclusion and a weight mask (bit 0 light, bit 1 heavy), scans list order and selects only a strictly nearer squared distance below 30000. Ties retain the first candidate. Neither query reserves or acquires an item.

## Entry, acquisition and completion

80094790 rejects an occupied secondary slot, then searches both weights. A candidate selects LightGet or HeavyGet and invokes 80094694, so true means pickup motion initialization began. The initializer clears throw flags, changes motion, and advances animation once or loops until throw bit 3 is consumed. The loop has no iteration or frame-exhaustion limit. Only afterward does it set the weight selector and damage callback. Heavy playback uses the scale helper; no numerical rate guarantee is inferred.

Anim consumes and clears bit 3 before making a fresh weight-filtered search. The item acquired may differ from the entry candidate, or no item may remain. Transfer writes the primary slot when empty, otherwise the secondary slot, with no local secondary-slot occupancy guard. Notification prioritizes the secondary slot and skips the character callback in that branch; the primary branch invokes the optional fighter callback before bookkeeping. Attachment chooses TopN for a light Warp Star, the light part for other light items, or the heavy part, followed by heavy pickup sound. Delegated item pickup callbacks can have their own effects.

At animation exhaustion, secondary item takes precedence. LightGet runs immediate effects and suppresses common completion only for Warp Star or Hammer. Non-LightGet with an item chooses Donkey-specific heavy waiting when x2222_b0 is set, otherwise LiftWait. Missing items and ordinary light completion use the common post-action helper with its exceptional neutral-state paths.

## Effects and interruption

Classification-5 handling distinguishes completion from cleanup. Both dispatch recovery, Bunny Hood, Metal Box, cloaking and consumable processing. Recovery calls conditionally add to Fighter's recovery accumulator; this review does not equate that call with immediate percentage subtraction. Normal completion enters WarpStarJump or Hammer state and returns true. Cleanup instead drops Warp Star with a zero vector and initializes Hammer state fields without invoking the normal entry wrapper.

IASA is empty, but it does not block collision or damage handling. Phys delegates grounded friction/movement. Collision failure calls 80094D90, which releases a primary heavy item, processes remaining primary then secondary immediate items, and enters Fall. Ordinary pickup damage calls 80094DF8 to process both occupied slots without a direct local motion change. Heavy pickup installs Lift's item-drop damage callback instead.

## AttackAir followup

The common AttackAir delayed-pickup timer path is unreachable in its current priority chain. To reach it, the immediately preceding attack checker must return false, establishing that pressed A is absent without changing input. The delayed predicate then requires pressed A and must fail. This proof does not depend on the earlier item/tether handlers. See attackair-followup.json for exact canonical evidence.

Immediate aerial pickup is different: it assigns and attaches the item, calls this TU's immediate-effect helper and reports acquisition accepted. Healing/status/consumption need not change motion; Warp Star/Hammer can. Grounded pickup entry changes to LightGet/HeavyGet, then waits for a later acquisition event. These are distinct success contracts.
