# Mario SpecialLw translation unit

## Scope and dispatch
The owned C file implements ten public `void(HSD_GObj*)` entry/animation/IASA/physics/collision functions, plus static startup, effect, rotation and transition helpers. The header declares the ten public functions and imports the HSD object forward declaration; its address comments are not compiled-layout evidence. Mario's active motion table assigns the paired animation, input, physics and collision callbacks to SpecialLw and SpecialAirLw with `FtMoveId_SpecialLw`. Dr. Mario's table uses these same callbacks. Thus this is shared Mario-family down-special implementation, not Mario-exclusive code. The conventional Mario Tornado mapping is supported by that dispatch and the explicit `x2234_tornadoCharge` data flow, rather than by numeric state names alone. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmario.c#L109-L130; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftDrMario/ftdrmario.c#L114-L135; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.h#L1-L18.

## Startup and state
Both entry functions clear command variable 2, request `ftMr_MS_SpecialAirLw` at frame 0 and rate 1, and call `ftAnim_8006EBA4`. Despite its ground-entry name, `ftMr_SpecialLw_Enter` does not request SpecialLw: it initializes vertical velocity to `vel_y - tap_y_vel_max`. Air entry subtracts zero when tornadoCharge is nonzero, otherwise subtracts tap_y_vel_max. Both clamp horizontal self velocity using air_momentum_x and run doStartMotion. That helper clears commands 0 and 1, sets groundVelX to zero, writes `(s32)(unk0 + 1)` to the otherwise unread local `unk`, clears isUnkColl, installs updateRot in take_dmg_cb and death2_cb, and starts effects. Command 3 is not explicitly initialized here. `unk0` and landing_lag are s32, not float attributes; an INT_MAX unk0 makes the signed addition overflow in the source language, and wrapping cannot be asserted without compiled evidence. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.c#L43-L112; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/types.h#L46-L57.

## Effects, ownership and callback lifetime
setGfx passes effect ID 0x47C, the fighter object, and its hsd_obj to efSync_Spawn, sets x2219_b0, and stores efLib_PauseAll/efLib_ResumeAll in pre/post-hitlag slots. The entry routines redundantly store the same pair after startup. No effect handle is retained, no allocation is owned explicitly by this TU, and no effect destruction is performed locally. Effect identity beyond ID 0x47C and full engine-managed lifetime remain unproved. updateRot obtains the Fighter and calls ftPartSetRotX(fp,0,0). Local animation cleanup clears only take_dmg_cb and death2_cb; it does not call updateRot or explicitly remove hitlag callbacks. Crucially, the common motion-change callback-reset block clears both interruption callbacks and both hitlag callbacks. The continuation helpers restore only hitlag callbacks, not updateRot. Therefore interruption cleanup must not be described as necessarily installed for the entire ground/air lifecycle. All substantive callbacks assume valid live objects, Fighter userdata, attributes and model/collision state; no local null validation or ownership transfer occurs. Static function pointers and coll_box do not point into stack storage. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.c#L22-L48; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.c#L114-L149; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/fighter.c#L1370-L1389.

## Animation and input
The ground animation callback does nothing locally while frames remain; otherwise it clears the two interruption slots and calls ft_8008A2BC. The precise shared-handler destination is not inferred here. Air animation first consumes nonzero command 1 and sets tornadoCharge to 1, independently of animation completion. At completion it clears the same slots, calls ftCo_Fall_Enter for integer landing_lag equal to zero, otherwise calls ftCo_80096900 with (1,0,true,1,(float)landing_lag). Negative integers take the nonzero branch; large s32 values can lose precision on float conversion but cannot produce NaN or infinity. The common fall-special helper normally enters FallSpecial and stores the landing lag, but x2224_b2 diverts to ftCo_80090780 before that setup. Subsequent landing also has a velocity-dependent branch rather than unconditionally applying special landing lag. Both IASA callbacks are empty; this proves only absence of work in those callbacks, not global uninterruptibility. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.c#L114-L153; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_FallSpecial.c#L28-L59; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftCommon/ftCo_FallSpecial.c#L145-L154.

## Physics and numerical boundaries
Ground physics starts with momentum_x. With nonzero command 0 it subtracts friction_end from the persistent groundVelX accumulator, adds that accumulator to the baseline and replaces a strictly negative result with zero. The misleading local name vel_y holds this horizontal bound until reused for vertical velocity. It calls ftCommon_8007CADC(fp,0,momentum_x_mul,bound), then ftCommon_ApplyGroundMovement. Independently, command 2 plus a B bit in pressed_buttons adds tap_y_vel_max to self_vel.y and invokes doPhys. There is no tornadoCharge gate in this ground branch.

Air physics requires tornadoCharge equal to zero, command 2 nonzero and the B pressed bit for ftCommon_Ascend. Ascend adds tap_y_vel_max and upper-bounds vertical velocity by tap_grav; tap_grav is not gravity in this call despite its name. FallBasic then always subtracts common gravity and limits downward speed by common terminal velocity. Horizontal processing uses air_momentum_x and air_momentum_x_mul with the same command-0 accumulator scheme, forwarding the result to ftCommon_8007D3A8. Air physics does not clear command 2 on a successful tap.

pressed_buttons is an edge-derived mask, computed from current versus previous held masks, optionally OR-accumulated under x2219_b5. It is not equivalent to B being held. Neither the local clamps nor shared helpers validate finite inputs or nonnegative attributes. Command-0-disabled baseline values are not locally zero-clamped; negative friction increases rather than decreases the accumulator; NaN fails the `< 0` comparison and is forwarded, positive infinity survives, and negative infinity becomes zero in the enabled local clamp. Equality and signed zero are not changed by that strict test. Thus unconditional nonnegative/decay claims require normal finite attribute assumptions. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.c#L174-L235; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftcommon.c#L462-L493; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/fighter.c#L1758-L1775.

## Ground/air continuation and collision
transition_flags combines KeepGfx, SkipHit, SkipMatAnim, UpdateCmd, SkipColAnim, SkipItemVis, Unk19, SkipModelPartVis, SkipModelFlags and Unk27. Unknown flag semantics are not renamed. doPhys clears command 2, calls ftCommon_8007D5D4, requests SpecialAirLw at the current frame with those flags, upper-bounds self_vel.y through ftCommon_ClampFallSpeed using tap_grav, clamps horizontal velocity, and restores effect hitlag callbacks. The canonical ClampFallSpeed implementation tests `self_vel.y > val`: it is an upper clamp, not a downward terminal-speed clamp. ftCommon_8007D5D4 also clears gr_vel and several motion components, sets jumpsUsed to 1 and locks ECB for 10; its rendered SetAirborne alias omits these side effects.

The source declares `static ftCollisionBox coll_box = {12,0,{-6,+6},{+6,+6}}`. Ground collision selects ft_80082888 only when ground_or_air equals GA_Ground, otherwise ft_800824A0. Either false result invokes doPhys and clears isUnkColl; a true result sets it without a local continuation call. Air collision always queries ft_800824A0; success runs doAirCollIfUnk, sets isUnkColl true, and failure clears it. The landing helper clears command 2, calls ftCommon_8007D7FC, zeros vertical velocity and tornadoCharge, requests SpecialLw at the current frame with continuation flags, clamps grounded velocity and reinstalls hitlag callbacks. The common grounded conversion resets jump/wall-jump state, unlocks ECB and asserts valid support; this helper is not merely a ground-state assignment.

Both collision callbacks finish with doColl. Only command 3 nonzero AND isUnkColl nonzero permits rotation `facing_dir * atan2f(floor.normal.x,floor.normal.y)` on part 0's X axis; otherwise it is reset to zero. The unusual atan2 argument order is intentional source behavior. No local check normalizes the floor normal, validates facing direction, or handles degenerate/nonfinite values; exact exceptional atan2f behavior remains unresolved. Contact-query internals and every side effect of the collision functions have not been proved by their rendered aliases. Evidence: code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.c#L155-L172; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/kinds/ftMario/ftmariospeciallw.c#L237-L310; code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/ft/ftcommon.c#L480-L594.

## Names and uncertainties
Canonical symbols govern this review. Rendered ftAnim_Advance, ftCo_FallSpecial_Enter, ftCommon_SetAirborne, ftCommon_SetGrounded, ftCommon_ApplyGroundAccelerationFromLStick and ft_CheckGroundWithCollisionBox are hypotheses, not independent evidence. The common airborne/grounded and fall-special implementations provide partial semantic corroboration but expose important omitted branches and side effects. The renderer also reports ambiguous identity for doColl; no cross-TU merge is proposed. The source proves a coll_box declaration and scalar literals, but not that the owned .data section is exactly that object, its compiled 24-byte extent, or the contents/layout of .sdata2. Those baseline section claims remain unresolved. Script timing for command variables, unk's wider consumers, all effect lifetime details, exact exceptional trigonometric behavior, and compiled ABI/register identity remain explicit uncertainties.
