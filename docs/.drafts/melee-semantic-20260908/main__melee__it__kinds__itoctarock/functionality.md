## Octorok behavior

The unit implements nine state slots with motion identifiers **0, 1, -1, 3, 2, 3, 4, 3, 3**. State indices and animation identifiers are distinct. State 5 alone has a null collision callback. [Table](code://c302741689bd67c361cd7faadb221df3193992c3/src/melee/it/kinds/itoctarock.c#L22-L77)

- **State 0 — wait/target acquisition:** loops animation and uses an attribute-loaded countdown before choosing continued waiting, turning, or attacking. Target classification uses inclusive horizontal and vertical bounds; equal X selects facing -1. Floor-relative velocity and orientation calls execute even on transition frames.
- **State 1 — turn:** initializes a countdown of 22 and clears bone-motion history. Animation updates derive velocity from bone 1 and reverse facing when the countdown is observed at zero. Completion enters wait and returns before decrementing the newly initialized wait timer.
- **State 2 — ordinary fall:** scales horizontal velocity by attribute x4, selects motion identifier -1, and delegates falling physics and landing recovery. The shared fall helper gates acceleration using the current speed; it does not clamp a post-update overshoot exactly to the configured limit.
- **State 3 — damage reaction:** supports both grounded and airborne behavior. Its animation restarts in air or returns to wait when grounded. The rendered `Jump_Anim` name is misleading; `Damage_Anim` better describes its caller and branches.
- **State 4 — rock attack:** initializes a countdown of 21, resets velocity and bone history, and marks airborne. At countdown zero, animation emits a stone from bone 14 using facing and special attributes, then requests sound 0x137. Completion reloads the wait timer, but the common final decrement still executes. This differs materially from turn completion. The x2C physics latch can be rearmed by collision processing.
- **State 5 — held:** pickup selects this state; animation loops, item-specific physics is empty, and collision is absent. Drop enters state 2; throw enters state 6.
- **State 6 — thrown:** loops animation, delegates falling physics, and uses shared contact handling with a null optional callback. Qualifying contact invokes shared response and generator notification before returning true.
- **State 7 — contact-responsive terminal outcome:** initializes airborne launch velocity, loops animation, and delegates contact response and contact counting. Empty item-specific physics does **not** mean stationary motion. The rendered `DeadGround` name and stationary explanations are corrected; the proposed conservative name is `DeadContact_Enter`.
- **State 8 — camera-directed terminal launch:** initializes velocity toward a randomized point near the camera and subsequently applies downward acceleration. Both animation and collision callbacks are inert false returns; descriptions of active terrain handling are corrected.

## Exceptional branches and lifetimes

Damage handling accumulates a shared hit contribution and uses a **strict greater-than threshold**, with state 6 as an independent terminal override. Terminal handling requests a small camera quake and randomly chooses state 7 or 8. The ordinary damage initializer preserves a surprising cross-file branch: already-airborne input to `it_8027B798` receives unprojected launch velocity but returns false, causing this caller to mark it grounded without the 0.2 upward clamp. This behavior is preserved rather than normalized into an expected airborne reaction. Turn and attack share persistent previous-bone translation storage. The final event wrapper forwards both pointers to reference cleanup and discards its boolean result. That helper clears matching owner, reflector, absorber, fighter and toucher references, resetting source-player attribution for one fighter-reference match; it does not itself destroy either object.
